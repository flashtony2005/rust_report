## 1. 总览：五层模型，一条主线

### 1.1 官方章节地图

润乾报表的文档把"非线性报表"拆成四个并列子模型（高级指南 → 非线性报表模型），另有一个平级的"填报表模型"：

```
高级指南
├── 非线性报表模型                  ← 本文主角
│   ├── 展现模型  zxmx36.html       报表长什么样：单元格、行列、合并
│   ├── 数据模型  sjmx43.html       数据从哪来：数据集、记录、字段、行集、分组
│   ├── 运算模型  ysmx46.html       格子怎么算：扩展、主格、层次坐标、格集、定位拉伸
│   │   └── 主格模型  zgmx48.html   （运算模型内嵌全节，另有独立页）
│   └── 子报表模型 zbbmx52.html     报表里嵌报表：引入式 / 嵌入式
└── 填报表模型  tbbmx55.html        （平级）采集模型 cjmx56 + 扩展模型 kzmx59
```

> 引用：`/report/senior/` 目录页实测层级（2026-10-14 抓取）。注意「填报表模型」**不是**非线性报表模型的子节，二者平级——填报表的"扩展模型"讲的是填报场景的维度格/数值格，与运算模型的"扩展单元格"是两个话题，勿混。

教程（`/report/tutorial/`）里与之对应的实践章节：

### 1.2 主线：数据 → 格 → 扩展 → 运算 → 展现

五个模型不是并列的目录分类，而是一条**单向依赖链**：

```
数据模型（数据集：二维表 + 记录 + 字段 + 行号#0）
   │  ds1.select(...) 等集合表达式给出"一个格子要变成几个格子"的答案
   ▼
运算模型（扩展模型：集合表达式 ⇒ 扩展格；主格模型：谁带着谁复制）
   │  扩展是"复制格子"，复制品与原格共享属性 ⇒ 主格树/层次坐标负责"复制后怎么定位"
   ▼
展现模型（类 Excel 的 N×M 矩形网格：扩展结果必须落回一张严格矩形的表）
   │  单元格属性、合并、区域划分决定最终绘制
   ▼
子报表模型（格中嵌表；引入式并入外网格 / 嵌入式保持独立）
```

官方在展现模型页开头点破了这条链：

> 「报表的展现模型严重关系到报表的绘制效率，而且数据处理模型对展现模型有一定的依赖性。」——`zxmx36.html`

也就是说：**展现模型是"地基"**——它是矩形网格，所以数据模型要能把数据组织成"往网格里填"的形态（行集/组集），运算模型要保证扩展后的结果仍是矩形（空白单元格占位），子报表才能有"引入式并入矩形"的可能。

## 2. 展现模型（Presentation Model）

### 2.1 官方定义

原文（`zxmx36.html`，逐句）：

> - **单元格**：「我们设计的展现模型采用类 excel 式的方案，即认为报表从外观上看是由 N 行 M 列的基本矩形的**格子**构成的平面图形，这些格子称为**单元格**。」
> - **合并单元格**：「如果选中一片连续的单元格区域（这片连续区域只能是**矩形区域**），把这片区域内的单元格全部合并成一个大的单元格，这个合并后的大单元格称为合并单元格。」
> - **行**：「由水平排列的一组单元格构成了**行**，在这里，行都有编号，从上到下依次为 1,2,3,4,……」
> - **列**：「由垂直排列的一组单元格构成了列，在这里，列都有编号，从左到右依次为 A,B,C,D,……」
> - **命名**：「单元格通过"列号+行号"来命名，例如：第 A 列第 1 行的单元格命名为"A1"。合并单元格以**左上角**的单元格编号作为合并格的编号。」
> - **报表**：「由单元格、合并单元格、行、列即组成了一个**二维矩形的表格**。表格中如果增加数据以及数据间的运算逻辑，即构成了报表。因此我们说，报表是由**表格、格中的数据以及数据间的运算逻辑**组成的。」

### 2.2 数据结构

展现模型的数据结构是三层嵌套（本项目建模口径，与产品实现逐一对应）：

```rust
// rpx-core：模板态（从 .rpx 文件读出）
ReportDefine {
    rows: usize,                  // 裸矩阵行数（含 0 号脚手架行，见下）
    cols: usize,                  // 裸矩阵列数（含 0 号脚手架列）
    row_cells: Vec<RowCell>,      // 每行的行属性：行高、行类型 rowType（-91/-95/-94/-90 等）
    col_cells: Vec<ColCell>,      // 每列的列属性：列宽等
    cells: Vec<NormalCell>,       // 普通格：按 (row,col) 索引的属性袋
}

NormalCell {
    row: i32, col: i32,           // 模板坐标
    row_merge: i32, col_merge: i32,  // 合并跨度（1 = 未合并）
    extensible: i8,               // 声明扩展模式：16/17/18/19（见 §5.3）
    expression: Option<String>,   // 表达式原文（属性袋里的表达式槽）
    value: Option<Value>,         // 字面量值
    props: PropSet,               // 其余属性码 20-94 的属性袋（format/disp_value/left_head 等）
}
```

三个结构性事实（决定了后面一切算法）：

**① 0 号脚手架行/列。** 矩阵有第 0 行与第 0 列，专门存放"不属于数据区"的东西——第 0 行放列头（列宽、列类型），第 0 列放行头（行高、行类型），`(0,0)` 是**根格（`0）**。因此产品口径的行数 = `矩阵行数 - 1`：

> 本项目实测：`IReport.getRowCount() = cellMatrix.getRowSize() - 1`，**模板态与计算态同一口径**（都不含 0 号行）。`ReportDefine2(a,b)` 构造器内部 `new Matrix(++a, ++b)`，**第一个参数本身已是该口径，不需要再 +1`**——历史上有一次实现把 `rpx-core::ReportDefine.rows`（裸矩阵行数）直接当口径用，少了 `-1`，被夹具抓住。（证据：`docs/m2-engine-design.md` §0.1；钉子测试 `rpx-engine/tests/units_contract.rs`）

**② 合并 = "铺满矩形 + 锚点唯一"。** 一个 `row_merge×col_merge = r×c` 的合并区，在矩阵实现上有两种建模（产品选后者）：
- 只在左上角存一份格，其它槽位**共享同一格对象引用**；
- 本项目阶段 A 建格时按产品语义："**先铺满矩形、后续格按自身内容覆盖**"——`Foo` 的非锚点槽在矩阵里也放指向锚点对象的引用，靠 `cell.getRow()==i && cell.getCol()==j` 判"谁是该槽的拥有者"。

这条"拥有者判据"后面反复出现：遍历矩阵时要跳过"被合并铺满的重复引用"，只处理拥有者（否则一个合并格会被算 N 次）。

**③ 空白单元格（内存优化）。** 官方在「定位和拉伸」一节给过设计动机：

> 「所谓空白单元格，就是不存储任何属性的单元格，他仅仅起个占位的作用，保证报表始终是个完整的矩形，因此在内存中他基本不占用内存。……当数据区向右、下进行扩展复制时，如果紧邻的右、下方有空白单元格，那么空白单元格的位置会被优先占用，之后才会继续向右、下复制。」

——这是**"矩形不变式"的代价与补偿**：扩展必须维持严格矩形（否则展现层绘制不了），但设计态往往左表头要 5 列、数据区只要 3 列，多出来的槽位用"零属性占位格"补上。本项目 M2 P0 不含"空白单元格优先占用"的复用逻辑（已声明缺口，§6.3）。

### 2.3 设计动机：为什么是"类 Excel"

三条动机，前两条官方明说、第三条从实现推出：

1. **绘制效率**（官方原文，见 §1.2 引文）：矩形网格的行/列是直接索引——第 r 行第 c 格的屏幕坐标 = 前缀和（行高/列宽累加），合并格只需锚点+跨度。任何"非矩形"模型（自由布局、流式排版）都要额外的碰撞检测与布局重算。
2. **数据处理模型依赖展现模型**（官方原文）：因为格是"行列坐标"寻址的，数据集才必须能给出"有序的一维序列"（行集）来填充扩展列/行——数据模型的行集概念正是为了对齐展现模型的网格。
3. **学习成本迁移**（从"类 excel 式"表述与教程定位推出）：用户已会 Excel，把"列号+行号+合并取左上角"照搬，设计器的心智模型是现成的。教程中大量表达式写法（`=ds1.sum(数量*单价)`、`=C8*E8`）就是 Excel 风格。

### 2.4 本项目的双矩阵：对展现模型的一处关键实证

官方展现模型页没有讲"计算时会不会动原网格"。反编译 + 探针实证给出的事实是：**产品在计算态维护两张矩阵**（本项目 `docs/m2-engine-design.md` §0.1、`docs/format-contract.md` 附件 I.9）：

| 矩阵 | 反编译名 | 角色 | 谁在读 |
|---|---|---|---|
| **引擎矩阵** | `_$25` | 只读的"模板镜像"：记录每个格**扩展前**的模板坐标、模板 head、模板属性 | `source` 字段（JSON 输出的 `calculated.cells[].source`）读它 |
| **计算矩阵** | `_$26` | 可变的"扩展后网格"：插行/插列、克隆格、head 指针都写它 | 值、`sub_cells`、渲染结果 |

两矩阵的最重要性状是一条**双向守门式**判据：

> `calculated.cells[].source != null` ⟺ `r ≤ 模板行数 && c ≤ 模板列数`（实测 6/6 夹具，越界 0 个、模板内缺 0 个）。

即：**"有 source"不是"这一格的出处"**，而是"计算态坐标仍落在模板矩形内"。这是本项目最容易误读的一条（`docs/m2-engine-design.md` §0.1 专门用一节讲这个坑）。它的价值：让对拍器能把计算态网格与模板网格对齐校验——扩展出的"新增行/列"没有 source，模板范围内的格子有。

## 3. 数据模型（Data Model）

### 3.1 官方定义：七个概念

原文（`sjmx43.html`）逐条：

**① 数据集**：
> 「我们定义数据集为一个由数据数组构成的**二维数据表**，其同列的元素数据类型都相同，为了方便，我们给数据集的列都起了一个**可唯一标识的名字**，列的名字和数据类型都保存在数据集中。」

**② 记录和字段**：
> 「考虑到关系数据库的习惯，同时为了和报表的行、列加以区分，我们把数据集的行称为**记录**，列称为**字段**。数据集中的记录都有**行号**，依次为 1,2,3,4,……获取数据集行号的书写规则为：`dsName.#0`（获得当前行的行号）或 `dsName.select(#0)`（获得数据集所有记录的行号）。其中 `dsName` 代表数据集的名字，**`#0` 代表第 0 列，即说明数据集的行号保存在第 0 列中**。」

**③ 行集**：
> 「数据集的行集定义为一些由数据集的行按某种顺序构成的**数组**，数据集本身也是一个行集。从组成元素上看，行集是数据集的子集，但排列次序未必与数据集的行序相同。」

**④ 分组与组集**：
> 「将数据集的所有记录按照一定的规则划分成 N 个行集的过程称为**分组**，分组后的每个行集称为一个**组**，多个组构成了**组集**。」

**⑤ 数据集函数**：
> 「能够对数据集的记录进行操作（取数、分组、运算等）的函数，我们称为数据集函数，其书写规则如下：`dsName.f(…)`。」

**⑥ 单源报表与多源报表**：
> 「当某个报表的数据来源只有一个数据集时，该报表称为单源报表；当某个报表的数据来源包括了多个数据集时，该报表称为多源报表。由于单源报表的模型是多源报表的子集，因此我们这里仅仅介绍多源报表。」

### 3.2 数据结构

```rust
// rpx-engine：运行期数据集口径（P0 子集）
DataSet {
    name: String,                 // 唯一名（ds1 / ds2 / …）
    fields: Vec<Field>,           // 列名 + 类型（同列类型一致）
    records: Vec<Record>,         // 记录数组（行）
}
Record { row_no: i32, values: Vec<Value> }   // row_no 即"行号列" #0
RowSet = Vec<RecordRef>                       // 行集：对记录的"有序引用序列"（可含排序、子集）
Group  = Vec<RowSet>                          // 组集：行集的数组
```

与官方概念的对应：

| 官方 | 实现物 | 本项目状态 |
|---|---|---|
| 数据集（二维表，列名唯一） | `ds1` / `ds2` 两张独立的表 | ✅ |
| 记录 / 字段 | `Record` / `Field`，同列同类型 | ✅ |
| 行号存 `#0` | `Record.row_no`；表达式 `ds1.#0` / `ds1.select(#0)` | ✅（`#0` 可解析） |
| 行集（有序子集/异序） | `ds1.select(...)` / `ds1.group(...)` 的产物 | ✅（select/group） |
| 分组、组集 | `ds1.group(字段)` 的产物 | 部分（M2 P0 只支持其作为扩展源） |
| 数据集函数 `dsN.f(...)` | `expr/dsfn.rs` 按名分派 | ✅（P0 子集：select/group/sum/count 等） |

一个易混点（官方在教程「多片扩展」页特别提醒过）：

> 「select() 函数选出了一组字段值，该组字段值保留了**一个指针**，指向数据集中的源记录，也就是说，该组字段值和数据集中的记录保持**一一对应的关系**，因此在当前格的附属单元格里（如 B2、C2），如果采取 `dsn.colname` 的表达式从当前数据集里取其他字段的值，**默认从当前主格指向的记录里取值**，而不需要到数据集中检索。因此，在当前格的附属格里建议尽量使用 `dsn.colname` 表达式，而不采用 `dsn.select(colname, filterexp, number)`，因为后者需要对表达式进行解析，**速度慢**。」——`dpkz101.html`

这就是**"数据集 current 指针"**模型：扩展格每复制一格，就把数据集 current 推进一步，附属格用 `ds1.字段名` 直接读当前记录。本项目把这套机制完整建模为 `calc/ds_current.rs`（触发器 = `(leftHead, topHead)` 对变了就重算；动作 = `cell.setDSCurrent`；"谁能灌 Row" = **只有 head 链上的扩展格**），见 `docs/m2-engine-design.md` §5.2。这条是本项目与手册**完全互相印证**的一条（§6.1）。

### 3.3 多数据集模型：为什么不做整合

这是数据模型里**设计动机写得最重**的一节，原文（`sjmx43.html`）：

> 「润乾报表的多个数据集**不需要进行整合运算**，而是**直接用于报表的运算**，在报表的运算过程中，通过一定的规则把多个数据集**关联**起来。」
>
> 「**数据集间的整合运算**是指将多个数据集通过类似数据库的 union、join 等操作，整合成一个数据集的过程。**整合运算极大的占用 cpu 资源，很多时候会导致数据量大大增加，对内存的占用也随之增加**。目前很多传统的报表工具号称支持多数据集，其实是把多个数据集通过整合运算，合并成一个数据集后，再运用于报表的运算，其实质还是单数据集模型。」
>
> 「当报表数据来自多个数据集时，如果采用单数据集模型，那么势必把三个数据集通过整合运算合并成一个数据集，然后进行交叉分组，其运算的复杂度大大增加，性能大大降低。因此我们说，**对于多源分片的报表，采用多数据集模型是最佳选择**。」

教程「多源关联分片的概念与特征总结」页把"多源 → 分片 → 必须直接基于多源"的因果说得更直：

> 「**多源**是指一个报表的数据来源来自多个物理数据表（或类似数据体），甚至是多个物理数据库。这里的"多个"常常不是两个三个，而是七八个乃至十几个。**分片**是指报表的纵向或横向或双向同时被分成了多个区域，每个区域独立扩展或者其中一个扩展区域为另一个扩展区域的子扩展区域，也可能是扩展区域和静态区域的混合。**关联**是指不同的扩展区域或者扩展与静态区域之间，数据存在着关联，不同区域之间的数据还可能进行运算。」
>
> 「**多源往往带来分片，正是由于分片，使得报表设计必须直接基于多源进行，而不能先将多源转成单源进行。有相当一部分分片报表无论如何也不可能转化成单源处理，部分能转成单源的报表处理也非常繁琐。**」——`dyglfpdgnytzzj105.html`

**"运算过程中关联"的具体机制**，教程「多片扩展」页给了标准例子（主子表）：

```
ds1：SELECT DISTINCT 订单.订单ID, 订单.客户ID, … FROM 订单
ds2：SELECT 订单明细.产品ID, 订单明细.单价, … FROM 订单明细

B2 单元格：= ds1.select(订单ID:1,,,订单ID)      ← 主表：按订单 ID 去重扩展
B8 单元格：= ds2.select(产品ID:1, 订单ID==B2,,产品ID)   ← 子表：用 B2 过滤
```

`ds2.select(..., 订单ID==B2, ...)` 里的 `B2` 就是"运算过程中的关联"——**B8 的每一格（对应一个订单明细）通过主格引用 B2（当前订单）来筛 ds2**。没有 join，没有临时表；关联发生在求值时刻，粒度就是"当前格的主格指向的那条记录"。

设计动机总结成三条：
1. **性能**：避免 union/join 的物化成本（CPU + 内存 + 中间结果膨胀）；
2. **能力**：部分分片报表（跨异构源、跨库）**在原理上无法**先转单源；
3. **语义**：分片本身就是"业务上无关的多主题共存"（见子报表模型页的表述："这些单元格片段和报表往往有一个共同的关注对象，但是同时各自又有一个独立的主题，片与片之间往往没有任何关联"），强行整合会引入无意义的笛卡尔语义。

### 3.4 本项目对照

- **`count` ≠ 数据集行数**：扩展格的复制个数取的是"**锚点表达式返回的 List 的 `size()`**"（`ExtExtendCell.java:379-380`）。`ds1.select(region)` 场景下二者恰好相等，带条件/多列的 `select` 则不等。这条是 `docs/format-contract.md` 附件 I.1a 的硬约束。
- **current 指针**：`calc/ds_current.rs` 建模了"谁把 ds.current 变成 Row"的完整闭环；探针 `ProbeDsCurrent` 三路独立印证（`docs/m2-engine-design.md` §5.2.6）。
- **多数据集**：P0 支持多数据集共存与 `dsN.f()` 分派；"数据集间的关联"（主格引用做过滤条件）已随主格链 + 表达式求值落地。

## 4. 运算模型（Computation Model）

官方把运算模型拆成五节：**基本概念 → 扩展模型 → 主格模型 → 层次坐标 → 格集 → 定位和拉伸**。本节按此顺序讲官方定义，并在每节末给出本项目对照。

### 4.1 基本概念

原文（`ysmx46.html`）：

> **集合**：「一些确定的事物汇集成为集合，构成集合的事物称为集合的元素或者成员。在润乾报表中，集合的元素一般是数据、单元格、行、列、记录、字段、组等。」
> **数组**：「将有限集的元素按照某种规则排序，得到一个有先后次序的序列，称为数组。数组的成员个数称为数组的长度。数组是集合的一种特殊情况。」
> **集合函数和操作符**：「运算结果为集合的函数，我们称为集合函数；运算结果为集合的操作符，我们称为集合操作符。集合函数有 `select()`、`group()`、`list()`、`query()`、`call()`、`to()` 等。」
> **集合表达式和单值表达式**：「计算结果为集合的表达式称为集合表达式。计算结果为单值的表达式称为单值表达式。」

这组概念是整个运算模型的**类型系统地基**：后面所有规则都能归约到"这个表达式是集合表达式还是单值表达式"。官方甚至直接把它定义为扩展的判据（§4.2）。

### 4.2 扩展模型（官方定义）

原文（`ysmx46.html`，与教程「多层交叉报表」页 `dcjcbb93.html` 完全一致）：

> **扩展单元格**：「当单元格的数据值表达式为**集合表达式**时，该单元格**默认**为可扩展单元格。可以为扩展单元格设置一个**扩展方向**，扩展可以有横纵两个方向，即横向扩展和纵向扩展，但**一个扩展格同时只能有一个扩展方向**。」
>
> **横向扩展**：「当可扩展单元格的扩展方向为横向时，该单元格进行的扩展称为横向扩展。此时该单元格会**横向进行复制**，复制出的单元格的数据值**依次为表达式的结果数据值**，表达式返回几个值，单元格就复制几个。**复制出来的新单元格的所有属性都引用被复制单元格的属性**。」
>
> **纵向扩展**：「……纵向进行复制……」（同上镜像）
>
> **不可扩展**：「当单元格的数据值表达式为**单值表达式**时，该单元格默认为不可扩展单元格。」

三个要点：
1. **判据是表达式类型，不是用户开关**："集合表达式 ⇒ 默认可扩展"——用户不需要声明"我要扩展"，写 `=ds1.select(x)` 它就是扩展格；写 `=C8*E8` 它就是单值格。
2. **一个扩展格只有一个方向**：横与纵是互斥的**属性**（不是两个独立开关）。这条对实现很关键：本项目 `extensible` 是一个字节（16/17/18/19），不是两个布尔。
3. **复制品的属性"引用"原格**：官方用词是"**引用**"被复制单元格的属性——不是深拷贝值，而是**共享属性来源**。这解释了为什么计算态克隆格要看 `source` 回指模板格（§2.4）。

### 4.3 主格模型（官方）

原文（`zgmx48.html` / `ysmx46.html` 内嵌全节）：

**根格（报表首格）**：
> 「报表左上角的灰色单元格称为报表首格，也称为根格。它用于**存储描述整个报表的属性**，同时他在层次坐标中有特殊的意义。根格（报表首格）的书写规则为：**`` `0 ``**。这里要强调的是 `` `0 `` 而不是 `'0`。」——对应实现里的 `(0,0)` 单元格（本项目 `CellId::ROOT`）。

**主格和附属格**：
> 「单元格进行扩展的过程中，缺省情况下，相对于其右（下）边的单元格而言，**扩展格是主动复制的**，被称为其它格（其右/下的格）的**主格**，而其右（下）的单元格是**被动跟随复制**的，被称为扩展格的**附属格或子格**。**主格和附属格是相对的概念**，即某格是另一格的主格或附属格，**不存在单独的主格和附属格**。从主格的定义中看，显然**只有扩展格才能是其它格的主格**！」
> 「要注意的是，在缺省情况下，扩展格**左（上）**的格**并不是**其附属格，**只有右（下）**的格才是其附属格。」

**左主格和上主格**：
> 「单元格进行**纵向扩展**时，我们又称其为其它格（其右/下的格）的**左主格**，而**横向扩展**时则称为**上主格**。一个单元格可以**既有左主格又有上主格**。」

**多层扩展与直接主格**：
> 「多个单元格同时进行扩展时，一个扩展格可以**既是某些格的主格又是另一个扩展格的附属格**……如果主格 A1 的附属格是 B1，而 B1 还有附属格 C1，那么 B1 称为 A1 的 1 级子格，C1 称为 A1 的 2 级子格……」 

**缺省主格认定**：
> 「单元格横向扩展时，**上方横向扩展单元格缺省为它的上主格**，下方单元格缺省为它的附属格；**如果上方没有横向扩展格，则上主格缺省为 `` `0 `` 格**。单元格纵向扩展时，**左边纵向扩展单元格缺省为它的左主格**，右边单元格缺省为它的附属格；**如果左边没有纵向扩展格，则左主格缺省为 `` `0 `` 格**。」

**人为改变主格规则（三个条件）**：
> 「Ø **左主格必须是纵向扩展格，上主格必须是横向扩展格**，否则设置无效。Ø **不允许出现循环设置**……出现循环设置时认为设置有误，**报表无法计算**。Ø **横向扩展格不允许有左主格，纵向扩展格不允许有上主格**。人为设置时，可能发生左（上）主格在右（下）边的情况，而且主格也不一定和附属格在同一行（列）上。」

**扩展变化规则**：
> 「多层扩展时，**扩展次序是从主到次的**，即先扩展主格，然后扩展其附属格，再扩展其二级附属格，依此类推。单元格进行**横向扩展**时，会将其**同列的上主格拉开（拉大）**，把其附属单元格复制，特别地，**如果其某个上主格不在同列上，则该上主格不会被拉大**；单元格进行**纵向扩展**时，会将其**同行的左主格拉大**，把其附属单元格复制，特别地，**如果其某个左主格不在同行上，则该左主格不会被拉大**。」
> 「主格能够主动进行扩展复制，称为**主动扩展格**；附属单元格被主单元格带动着复制，称为**被动复制格**……既不能主动扩展复制，也不能被动复制的单元格，我们称为**不可复制格，或者叫固定格**。」
> 「同一报表中可能同时有纵向扩展格和横向扩展格，如果它们的子格有重叠部分，则这些子格就**既有左主格又有上主格**，在扩展时会被**既向下又向右**复制，形成一片矩形单元格区域，从而做到**交叉扩展**……单元格的横向扩展与纵向扩展这两种扩展是**相互独立**的，既可以先进行横向扩展，也可以先进行纵向扩展，**并不会影响扩展之后的结果**。」
> 
> 「**同一行（列）上有两个或更多的扩展格。左（上）边的扩展格将是右（下）边的扩展格的主格**，右（下）边的扩展格是其左（上）边扩展格的附属格，同时又是其右（下）边单元格的主格。」——同层扩展格之间**自左向右/自上向下**也构成主格链。

**缺省引用规则（格间运算的定义）**：
> 「缺省情况下，在单元格中的运算中可以引用其它单元格的值，**直接写单元格名即可，这样的运算称为格间运算**……被引用的单元格**必须是能够由当前格唯一确定的**。一般情况下，被引用单元格往往是**当前格的主格**，或者**与当前格有相同的一级主格**，或者是**固定格**。固定格由于不能复制，因此可以唯一确定。」

最后这条"唯一确定"是**扩展模型的安全阀**：扩展后一个模板格会变成 N 个实例，如果随便引用就会出现歧义；主格树保证"当前格 → 沿主格链上溯"路径唯一，所以能唯一落格。

### 4.4 层次坐标与位移坐标（官方）

**动机**（原文）：

> 「在进行报表设计时，单元格尚未进行扩展，但是其它某些单元格的表达式往往需要对这个单元格**扩展后的单元格**进行精确定位并运算。……然而 B2 能扩展出几个格子以及每个格子在什么位置，**在扩展前很难描述**，因此，为了避免混淆，应该对扩展后的每个单元格进行**唯一性定义**，这就是单元格的**层次坐标**。层次坐标是用于唯一描述（精确定位）扩展后的每一个单元格的表达式。」

**层次坐标语法**（以文本可还原的形式）：

```
cellx[ Lk:lk, Lk-1:lk-1, … L1:l1 ; Tk:tk, Tk-1:tk-1, … T1:t1 ]
```

> （a）`Lk` 为 cellx 的左主格，`lk` 为左主格扩展后的次序（第几个），**不指定或为 0 表示"当前表达式所在单元格所属的当前左主格"**；`Tk`/`tk` 类似为上主格次序。
> （b）只有上主格没有左主格时，**分号不能省略**：`cellx[;Tk:tk,…,T1:t1]`；只有左主格时，**分号可以省略**。
> （c）次序**从远到近**（越上级的主格越靠前）；查找顺序**从最上级的主格开始**。
> （d）「**完整的层次坐标表达式应该包括 Cellx 的所有主格**，层次坐标**与写在哪个单元格中无关**。」

**位移坐标（相对定位）**：

> 「有了层次坐标后，很多时候并不够用，因为大部分时候报表设计者**并不知道目标单元格的具体位置，仅仅知道目标单元格相对于当前单元格的位置**……这种涉及到相邻 n 行或者 n 列的行间、列间的运算，称为**位移运算**……位移坐标是用来描述**目标单元格和当前格之间的位置关系**的表达式。」

语法与层次坐标同形，但 `lk`/`tk` 是**偏移量**（`±`）：

```
cellx[ Lk:±lk, … ; Tk:±tk, … ]
```

> 「完整的位移坐标表达式应该包括 Cellx 的所有主格，**位移坐标与写在哪个单元格中紧密相关**。」（对比层次坐标"与写在哪个单元格中无关"——这是两者的本质区别。）

**根坐标表示法**：

> 「完整的层次坐标是从根上开始的……`` cellx[`0, Lk:lk, …; `0, Tk:tk, …] ``，而 `` `0 `` 则代表根坐标。」

**`&` 运算符（层次坐标的逆运算）**：

> 「如何知道某个扩展出来的格子在所有扩展出来的格子中排第几呢？此时我们就引入了 `&` 运算符，他可以**获得当前格所属的某主格在所有扩展出来的格子中排第几**……`&cellx` 返回整数，当前格所属的 cellx 主格在所有扩展出来的格子中的排序。**cellx 必须是当前格的主格**。」

教程末页（`dtgjysdgnytzzj147.html`）把这类运算的总称与特征归纳为：

> 「**自由格间运算**是复杂报表另一个典型特征。……特指**浮动行列**的情况，即行列均为动态扩展出来的，此时行间、列间、甚至组间的运算。自由格间运算有如下特征：1、行列浮动；2、运算可能跨行、跨列，还可能跨组；3、**行列对称**：运算可能是纵向的行间组间运算，还可能是横向的列间、组间运算；4、**单元格的定位不仅仅靠位置，还可能根据复杂的条件来定位**；5、**独立格运算**，即位于扩展区域之外的某些独立的格子，需要引用扩展区域内的单元格的值；6、**序号**，为扩展出来的格子编号，可能存在多种编号方式。」

### 4.5 格集（官方）

> 「在实际应用中，往往需要对**一组**单元格进行运算……为了能在表达式中描述确定的一组单元格，我们引入**格集**的概念。**格集可以看为满足某种条件的一组单元格的集合**。特别的，单个单元格也可以视为仅含一个单元格的格集。」

**固定格的格集表示法**：

> 「`list(Cell1, Cell2, Cell3,……Celln)` 表示由 Cell1, Cell2, Cell3,……Celln 组成的格子的集合；**`[Cellx : Celly]`** 其中 Cellx 与 Celly 均为单元格，该表达式表示**以 Cellx 与 Celly 为对角点圈起的矩形区域**，而且，**Cellx 在左上角，Celly 在右下角**。」
>
> ⚠「**Link 操作符返回的结果是一个格集**，可以对其应用集合函数，如 `count()`、`sum()`、`max()`、`min()` 等，**但是包含 link 操作符的单元格不允许设为扩展格**。」
>
> 举例：「`list(A1,B3,C4)` 表示由 A1,B3,C4 三个单元格组成的集合；**`sum([A1:B3])`** 表示对以 A1 与 B3 为对角点圈起的矩形区域里的格子求和。」

**扩展格的格集表示法**：

```
cellx[层次坐标或者位移坐标]{}
```

> 「格集相当于在层次坐标或者位移坐标的基础上增加了 `{}`，即可表示该层次坐标或者位移坐标**界定的范围内的所有单元格**。前文已经提到，如果没有 `{}`，而层次坐标界定的范围内的单元格不止一个，那么该层次坐标返回的是该范围内的**第一个**单元格的值，有了 `{}`，就返回该范围内单元格的**集合**。」
> 例：「``C2[`0]{} `` 返回扩展后的 c2…c12；`C2[A2:2]{}` 返回扩展后的 c7…c12；`D2[A2:1,B2:2]{}` 返回扩展后的 d4,d5,d6。」

**条件表达式**：

```
cellx[层次坐标或者位移坐标]{条件表达式}
```

> 「其含义是对层次坐标或者位移坐标界定的单元格集合**再运用条件表达式进行过滤**，把符合条件的单元格找出来。」

**`$` 运算符**：

> 「此时我们往 d2 单元格中写入表达式：`C2-C2[A2:-1]{当前格的b2主格值==目标格的b2主格值}`。这时我们会发现，条件表达式没法写了，当前格的主格是 b2，目标格的主格也是 b2，如果我们写成 `b2=b2`，显然搞不清谁是谁的，于是我们引入了 `$` 运算符，他**在格集条件表达式中指代当前格的主格**。例如上面的条件表达式我们可以写成：`C2-C2[A2:-1]{$B2==B2}`，其中 **`$B2` 指代当前格的 B2 主格，`B2` 指代目标格的 B2 主格**。」

### 4.6 定位和拉伸（官方，属分页/区域层）

原文要点（`ysmx46.html`）：
- **报表区域**：「横向分区从左到右的顺序为：左表头 → 常规列 → 右表头；纵向分区从上到下的顺序为：分页页眉 → 头标题 → 报表头 → 分组表头 → 数据区 → 表尾区 → 尾标题 → 分页页脚。区域顺序……不可颠倒；除了数据区，其它区域可以不存在；**合并格不能跨越区域**，否则分页时会出现混乱；除报表头、分组表头、数据区和表尾区以外的区域适用定位和拉伸规则。」
- **空白单元格优先占用**（§2.2 ③ 已引）。
- **分页时伸缩规则**：「报表头、分组表头、数据区、表尾区横向扩展时，其它区域的单元格**从右往左数，找到第一个设置"分页时伸缩"属性的单元格，对其进行拉伸**。如果没有单元格设定了分页时伸缩，则对最右边一个单元格进行拉伸。」
- **位置不变**：「……其它区域的单元格除了向右靠齐和被拉大的单元格，**其余单元格保持位置不变**。」

这一节是**展现层对扩展的"配合收尾"**：数据区扩展后，标题区/页脚区靠什么规则对齐（伸缩一格 + 其余不动）。它解释了为什么扩展算法只负责"网格生长"，而"标题怎么对齐"是另一套规则——本项目 M2 P0 不含定位/拉伸（缺分页区域模型，已声明缺口）。

## 5. cell 扩展算法详解（本项目口径）

> 本节讲**产品实际怎么算**。正文口径以 `docs/format-contract.md` 附件 I（扩展算法逐行契约，【已核实】）与 `docs/m2-engine-design.md` §12（执行顺序清单）为准；Rust 实现落点 `crates/rpx-engine/src/ext_algo/`。
> 一句话总览：**扩展 = 在一个两层"包络带"内，把带内格整块复制 N-1 份、插进新行/新列，再修 head 指针与合并跨度。** 难的不是复制，而是"谁算谁的包络、head 指到哪里、什么时候插、插完谁来用"。

### 5.1 全景：从模板到计算态的三阶段

产品的 `Engine.calc()` 计算链路（本项目按此划分为三阶段实施）：

```
.rpx 模板
  │ ① 阶段 A：建格（stage_a.rs）
  │    模板格 → 计算矩阵初始态：每个槽位放一份"格对象"（合并区铺满 + 锚点唯一）
  ▼
【阶段 B】prepareCalculate（stage_b.rs）—— head 图 + extensible 改写
  │    第 1 步：行优先遍历，决定"谁是扩展格（ExtExtendCell）"
  │    第 2 步：行优先遍历，为每格算 左 head / 上 head，并执行 16 → 17/18/19 改写
  │    第 3 步：把 head 链"归一"到最近的扩展格（+ $5/$6 子格登记的副作用）
  ▼
【阶段 C】求值调度（eval/sched.rs → calc/run.rs）—— 显式状态机
  │    19 先行（横向）→ 18（纵向）→ 17（公式格）→ special
  │    扩展格求值：求表达式 → 是 List？→ 调 extend_row / extend_col → 逐实例填值
  ▼
计算态网格（两矩阵：_$25 模板镜像 + _$26 计算态）+ 逐格值
  │  M2-11 分页（pager.rs）→ M2-08 mergeSame（merge/）→ 序列化对拍
  ▼
expected.json（计算态 + 分页态对拍基准）
```

### 5.2 阶段 A：模板 → 计算矩阵（建格）

三件事（`rpx-engine/src/stage_a.rs`）：

1. **槽位铺格**：遍历模板 `NormalCell` 列表，对每个格按 `(row_merge, col_merge)` 把矩形 `[row, row+row_merge) × [col, col+col_merge)` 的槽位全部填上"指向该格对象"的引用；**先铺满、后续格按自身内容覆盖锚点槽**（模板合法性由 M1 装载保证）。
2. **脚手架**：第 0 行/列（`RowCell`/`ColCell`/根格 `(0,0)`）按原样进矩阵，成为 `CellId::ROOT`（根格）与头行/头列，不参与扩展。
3. **归属判据**：之后所有遍历用 `cell.getRow()==i && cell.getCol()==j` 判"谁是槽的拥有者"——**这条判据在阶段 B、C 与扩展算法里被反复使用**，别改成"格存在即处理"（合并区会被重复触碰）。

### 5.3 阶段 B：prepareCalculate —— 谁扩展、谁带谁（**顺序即契约**）

`ExtCellSet.prepareCalculate`（`ExtCellSet.java:721-807`）分**四步，顺序不可换**（`docs/m2-engine-design.md` §4）：

```
第 1 步  行优先遍历，决定"谁是 ExtExtendCell（扩展格）"            :745-758
第 2 步  再次行优先遍历：算左 head、算上 head、执行 16→17/18/19 改写 :771-782
第 3 步  把 head 链"归一"到最近的 ExtExtendCell                     :783-806
```

**为什么顺序不可换**：第 2 步算 `cell` 的 head 时，"它左边/上边"的格**必须已经算完 head、也已完成 16 改写**（扫描是行优先 `i` 升序、`j` 升序）——否则 head 链会指向"还没定性的格"。这条顺序是后面所有结论的前提。

#### 5.3.1 第 1 步：谁会成为扩展格

对每个拥有者格：

```java
this._$21 = cell;
if (!cell.checkExtend(ctx)) continue;      // 不通过 → 保持 ExtNormalCell
cell = this._$1(cell);                     // 通过 → 换成 ExtExtendCell
```

`checkExtend`（`ExtNormalCell.java:492-514`）：

| 声明 `extensible` | 有表达式时返回 | 无表达式时返回 |
|---|---|---|
| 16 | `expression.isExtend()`（表达式**可扩展**才 true） | `false` |
| 17 | `false` | `false` |
| 18 / 19 | `true` | `true` |
| 任何值 | `cellType ∈ {-61 图形, -57 条形码, -60 子报表}` 一律 `false`（**最开头，优先于一切**） | 同 |

三条硬结论：
- **判据是"表达式可扩展"（`isExtend()`），不是"用了 DS 函数"**。`isExtend()` 是解析树上的一次**纯递归谓词**：`true ⟺ 树里至少有一个"扩展源节点"`（DS 选择类函数 / 排序切分类函数 / 值是 `List` 的字面量）。⛔ 用 `isDSFunction()` 近似会错：`sum(ds1.select(qty))` 的 `isDSFunction()=true` 但 `isExtended()=false`（`Function`/`Sum` 都没重写 `isExtended`），且 `Sort`/`To`/`Constant(List)` 的 `true` 不来自 DS 函数。两个谓词**传播规则相反**，都要实现。完整真值表见 `docs/m2-engine-design.md` §13.3。
- **类型短路（`-61/-57/-60`）在函数最开头**：这三类格即使声明 18/19 也**不是扩展格**，直接掉回普通格规则。⛔ 7 个夹具里都没有这三类格——**漏掉这句短路，没有任何测试会失败**（是一个可构造的真实分叉，本项目把它写成了具名常量 `EXTEND_EXCLUDED_CELL_TYPES` + 钉子测试）。
- **无表达式时 16/17 一律不是扩展格**，18/19 恒是（`:513`）。

#### 5.3.2 第 2 步：head 的赋值（两函数**四处不对称**）

对每个拥有者格：**先算 head，再改写**：

```java
this._$21 = cell;
cell.setCellLeftHead(this._$3(cell));   // 左 head：找"纵向扩展的主格"
cell.setCellTopHead (this._$2(cell));   // 上 head：找"横向扩展的主格"
cell.prepareCalculate(ctx, macros);     // 16→17/18/19 改写（读上面两个 head）
```

**head 查找的语义**（两个方向镜像，可照写为一份泛化 `find_head(dir)`）：

```
fn find_left_head(cell):
  A. 模板声明了 leftHead（属性码 30）→ 校验不成环后直接用（人为改变主格）
  B. 同行向左扫（列号 cell.col-1 递减到 1，不含 0 号头列）：
       h = 计算矩阵.get(cell.row, col)
       跳过的情形：空槽 / 合并块且 ext≠18 且不在本行 / 声明成环
       命中的情形：h.containRow(cell) && h.ext==18    ← 只有 18 走这条
          → 校验无环后【直接返回 h 本身】
       其它情形：返回 h 的 head（head-of-head），并顺手"自愈"坏链
  没命中 → 返回 ROOT（根格）
```

**四处不对称**（`docs/m2-engine-design.md` §4.2 实测表）：

| 维度 | `_$3`（左 head） | `_$2`（上 head） |
|---|---|---|
| 扫描方向 | `col` 递减 | `row` 递减 |
| 合并跳过条件判的 extend | `18 != ext` 才跳 | `19 != ext` 才跳 |
| **是否调 `sameRowTypeAs`** | **从不调用**（用 `containRow`，与行类型无关） | **调两次**（命中分支 + 硬门槛） |
| 命中"本格包住它"分支的判据 | `head12.containRow(cell)` | `cell.sameRowTypeAs(head12) && head12.containCol(cell)` |

> ⛔ 给两函数写一份"共用逻辑"会同时踩两个坑。本项目实现为一份泛化函数 + 参数化的方向差异（`heads/find.rs`）。

**净效果（探针 `ProbeHeads` 实测，`engine_ext` 全部 12 个模板格）**：

| 断言 | 实测 |
|---|---|
| `top_head == cell00`（根格） | **12/12 成立** |
| `left_head == cell00` | **10/12 成立**；两个例外 `(3,2)`/`(3,3)` 指向 18 锚点 `(3,1)` |

——上 head 全归根格；**左 head 会被左方的 18 锚点截断**（这正是"命中分支直接返回 h"的效果）。

#### 5.3.3 第 3 步：`extensible` 的两条写入路径（16 → 17/18/19）

这是"所有公式格在计算态 `extend != 16`"的**真正机制**——**两条路**：

| 格 | 走哪条 | 结果 |
|---|---|---|
| 被包装成 `ExtExtendCell` | `ExtExtendCell.prepareCalculate:314-353` | 声明 **16** 的按**拓扑**改写：`(cell00,非cell00)→19`、`(非cell00,非cell00)→17`、其余→18；声明 17/18/19 **原样** |
| 未被包装，仍是 `ExtNormalCell` | `ExtNormalCell.prepareCalculate:528-563` | **`if (expression != null) setExtensible(17)`**（`:539-541`）——**无条件**置 17，与拓扑无关 |

> ⛔ **只实现一条会"因错得对"**：`engine_sum` 里 `(2,3)..(2,9)` 恰好 heads 为 null 也给出 17，看似拓扑公式对；一旦某普通公式格 heads 落在 `(cell00,cell00)` 就会判成 18 而错。两条路都只在 `expression != null` 时改写 ⇒ **无表达式的格保留声明值 16**（6 夹具共 72 个格）。
>
> 🔑 **值写入的守卫同源**：字面量写值发生在 `expression == null` 的分支（`ExtNormalCell.java:541-542` 与 **`ExtExtendCell.java:331-332`** 两处）——后者是"声明 18/19 且**无**表达式"的格，它被判成扩展格却**依然写值**。用"角色是 Literal"当守卫会静默漏值；正确守卫是 `expression == null`（本项目实现为 `stage_b.rs` 的 `has_expr` 平行数组）。

**16/17/18/19 的语义汇总**（本项目实现口径）：

| 值 | 含义 | 来源 |
|---|---|---|
| 16 | **声明默认值**（未改写）：无表达式的格保留它 | 模板属性 |
| 17 | 普通公式格（不主动扩展、不被动复制？——实为"公式格"标志） | 两条路径改写 |
| 18 | **纵向扩展格**（`extend_row`） | 拓扑改写或声明 |
| 19 | **横向扩展格**（`extend_col`） | 拓扑改写或声明 |

#### 5.3.4 第 4 步：head 链"归一"

把每个格的 head 链**归一**到最近的扩展格（`ExtCellSet.java:783-806`），并产生副作用：`setCellLeftHead`/`setCellTopHead` 会把本格**登记进 head 的 sub 列表**（`_$6` 左子格列表 / `_$5` 上子格列表）——只有 head 是扩展格时才登记（`ExtCell.java:122-124` 基类空实现，仅 `ExtExtendCell.java:100-117` 有实体）。`head==self` 报 `leftHeadCircle`（→ `CircularRef`）。

### 5.4 阶段 C：求值调度器（**为什么不照搬 Java 的异常协程**）

产品用 Java 异常做"协程式"调度：`_$4/_$3` 等返回状态码（`4`/`5` 压栈换格、`1` 终止、`6`→special、`8`→`_$24`），配合 `try/catch` 跳出/恢复。**Rust 没有异常协程**，本项目改写成**显式状态机**（`eval/sched.rs`：`NeedCell{cell,state}`；`docs/m2-engine-design.md` §5.1 三条接线约束、§5.4 四条硬约束）：

```
求值顺序（产品口径）：
  19（横向扩展）先 —— 横向定列
  18（纵向扩展）后 —— 纵向定行
  17（公式格）
  special（-90 分组头等）
```

产品的硬约束（逐条有 `file:line`，见 `docs/m2-engine-design.md` §5.3）摘要：
1. `engine.calc()` 按 `rowType` **级别 1..20** 分轮；
2. **19 必须先于 18**：顺序反了 19 锚点子格会落在第 4 行而不是第 8 行（实测 V9）；
3. 扩展格的"插行/插列"发生在**求值循环内部**（表达式算出 List 之后才调 `extend_row/col`），不是预处理。

> 🔑 **设计动机**：Java 的异常协程把"控制流"藏在异常类型里（哪类异常=回到哪层），可读性极差但能省掉状态字段；Rust 用 `Result` + 显式 `State` 枚举把同一控制流**摊平**成可测试的状态迁移。本项目为此写了「三条顶层接线约束」与「四条硬约束」作为移植纪律（`docs/m2-engine-design.md` §5.1/§5.3）。

### 5.5 扩展本体：`extendRow` / `extendCol`

正文以 `docs/format-contract.md` 附件 I 为准（逐行契约）。要点重述：

#### 5.5.1 唯一调用点与 `count` 的来源（附件 I.1）

`extendRow`/`extendCol` 在整个产品里**只有一处调用**：`ExtExtendCell.calculate`（`ExtExtendCell.java:426-430`）：

```java
if ((result = ...calculate(ctx)) instanceof List) {          // :376
    int len = list.size();                                    // :379-380
    if (len == 0) { this.setValue(null); return; }            // :381-384  ← 空 List 不扩展
    ...逐元素记 valList/dispValList/formatList...
    if (18 == extend) this.engine.cs.extendRow(this, len);    // :426-427
    else              this.engine.cs.extendCol(this, len);    // :428-429
    for (i = 0; i < len; ++i) { cell = this._$7[i]; cell.setValue(valList[i]); ... }  // :431+
}
```

四条硬约束：
- **`count` = 表达式结果 List 的 `size()`**，不是"数据集行数"（`ds1.select(region)` 场景二者恰好相等，带条件/multi-column 的 select 则不等）；
- 结果**不是 List** ⇒ 完全不扩展；
- `len == 0` ⇒ **不调用** `extendRow/Col`，锚点 `setValue(null)` 后 `return`（"空数据集 ⇒ 行数=模板行数"是产品行为，不是我们的约定）；
- `18 → extendRow`；其余（19）`→ extendCol`。

⚠ **`count == 0` 不许进 `extend_row/extend_col`**：`new ExtCell[count]` 之后**无条件**写 `extCells[0] = cell` ⇒ 传 0 会 `ArrayIndexOutOfBoundsException`。产品靠上游那句 `return` 兜住；**Rust 侧必须自己也兜**（我们的调用方是我们自己的代码，不能继承"上游保证 count≥1"的假设）——`count == 0` ⇒ 不扩展 + 该格值置空，**绝不 panic**。

#### 5.5.2 包络（`rows`/`cols` 从哪来）（附件 I.2）

| 量 | 方法 | 定义 | 递归方向 |
|---|---|---|---|
| `beginRow` | `_$4(cell)` `:928-939` | `min(cell.getRow(), min over leftSubCell 递归)` | **左**子格链 |
| `endRow` | `_$3(cell)` `:940-951` | `max(cell.getRow()+getRowMerge(), max over leftSubCell)` | **左**子格链 |
| `beginCol` | `_$2(cell)` `:1059-1070` | `min(cell.getCol(), min over topSubCell)` | **上**子格链 |
| `endCol` | `_$1(cell)` `:1071-1082` | `max(cell.getCol()+getColMerge(), max over topSubCell)` | **上**子格链 |

```
rows = endRow - beginRow      // 半开区间 [beginRow, endRow)
cols = endCol - beginCol
```

⛔ **行包络沿 `leftSubCell` 递归、列包络沿 `topSubCell` 递归**——方向搞反会得到错的带高。直觉：纵向扩展的作用域由"左 head 链"决定（左主格家族）；横向由"上 head 链"决定。单格无子格时包络 = 自身（`rows = row_merge`）。

#### 5.5.3 插行 / 插列（附件 I.3）

- **插行 `_$3(row, count)`**：只有**主格自身的 `row`** 被平移（`cell.addRow(count)`）；合并块内非锚点槽靠"跳块"跳过；插行是**全表平移**（2 参版）。
- **插列 `_$2(col, count)`**：**部分平移**——`Matrix.insertCols(col,count,begin,end,align)` 只平移**行头行区间**内（+可选第 0 行）的格，**带外行原位不动、新列留空**。这就是 `engine_ext` 里 `B1/C1/D1` 被挤到 `(1,6)/(1,7)/(1,8)` 的机制（探针实证）。
- **"行头行"判定**（`_$2(int row)` `:846-857`）：`row == 0` → true；`get(row,0) == null` → true；否则 `rowType ∈ {-91, -95, -94, -90}` → true。即 **行头行集合 = {0} ∪ {rowType ∈ {-91,-95,-94,-90}}**。

⛔ **`_$n` 存在多重载、语义互不相干——这是最容易读错源码的地方**：`_$3(int,int)`=插行 / `_$3(int)`=删行 / `_$3(ExtNormalCell)`=**找左 head** / `_$3(ExtCell)`=**包络结束行**；`_$2` 同理四义。在 `extendRow/Col` 内部形参是 `ExtCell`，走的都是**包络支**；别被同名的 head 查找方法带跑。⚠ 还有一条：`_$8()` 是**中断检查**（cancel 钩子），不是矩阵操作。

#### 5.5.4 `extendRow(cell, count)` 两趟（附件 I.5）

```
beginRow = _$4(cell); endRow = _$3(cell); rows = endRow - beginRow;
extCells = new ExtCell[count]; extCells[0] = cell; cell.setExtCells(extCells);
① _$3(endRow, rows * (count - 1));            ← 在 endRow 处插 rows*(count-1) 行
② cell.expandLeftHead(rows * (count - 1));    ← 沿左 head 链撑大 rowMerge（"拉大主格"）

第 1 趟（克隆，:1000-1029）：
  for m = 1..count-1:
    for i = beginRow..endRow-1:
       k = m*rows; x = i + k;
       行内第 0 列脚手架：cells2[0] = clone(cells1[0]); addRow(k)
       对每个带内格 sub（拥有者 + cell.isLeftHeadOf(sub)）：
          newSub = clone(sub); newSub.addRow(k);
          铺满 [x, x+getRowMerge()) × [j, j+getColMerge()) ← newSub   ← 合并块整体铺
          if sub == cell: extCells[m] = newSub; newSub.setExtCells(extCells)
       j += sub.getColMerge() - 1                                     ← 跳块

第 2 趟（修 head，:1030-1056）：
  for m/带内格:
     if sub != cell: newSub.setCellLeftHead(平移后的 head)
     if topHead != root: newSub.setCellTopHead(top)   ← 原样共享（除非 root 则不动）
```

三条易错点：
1. **克隆判据 `cell.isLeftHeadOf(sub)` 是自含的**：`isLeftHeadOf` 从 `sub` **自身**起步沿链上溯 ⇒ `cell.isLeftHeadOf(cell) == true` —— **锚点自己天然被复制**，这正是 `if (sub == cell)` 分支能命中的原因；
2. **只克隆"左 head 链覆盖到"的格，不是整条行带**；带内其它格不复制，合并区靠"整块铺满"补回；
3. **第 2 趟只平移 `leftHead`；`topHead` 原样共享**（纵向复制时"本格上方那格"不变）。

#### 5.5.5 `extendCol(cell, count)` 两趟（附件 I.6）

与 `extendRow` 镜像，但有**四个不对称点**：
1. **前置校验**：只有"行头行"上的格才允许列扩展，否则抛 `ReportError`，消息键 **`ExtCellSet.entendCol`**——⚠ 产品把 `extend` 拼错成 `entend`，**逐字照抄，别"纠正"**；
2. **第 0 行列头是显式逐个克隆的**（`extendRow` 里是 `cells2[0]` 单行）；此外第 1 趟里 `sub.leftHead == root` 的格会 **`root._$6.add(newSub)`**（登记到 root 的左子格列表）；
3. **`extend_col` 的施力点是 `cell00._$5`（上子格列表）中 `containCol(anchor)` 的成员**——⛔ 写成"沿锚点的 head 链给每个 head `addColMerge`"会得到与夹具**完全相反**的 `col_merge`（`cm=(4,1)=5` vs 实测 `1`）；
4. **第 2 趟 `leftHead` 分三支**：`root` → 不动；**带内** → 平移；**带外** → 原样保留。而 `extendRow` 的第 2 趟没有"带内/带外"之分，直接平移。**这是两个方向最容易写错的不对称点。**

#### 5.5.6 对称性总表与五个最容易做错的点

对称性总表（附件 I.7，实现时对照）：

| | `extendRow`（纵向，18） | `extendCol`（横向，19） |
|---|---|---|
| 前置校验 | 无 | 行头行校验，否则 `ReportError("ExtCellSet.entendCol")` |
| 包络递归方向 | **leftSub** | **topSub** |
| 插入 | `_$3(endRow, rows*(count-1))` | `_$2(endCol, cols*(count-1))` |
| 脚手架克隆 | 行内 `cells2[0]`（单格） | **显式 for 循环**（每个带列） |
| 复制判据 | `cell.isLeftHeadOf(sub)` | `cell.isTopHeadOf(sub)` |
| 第 2 趟 leftHead | **直接平移** | **带内平移 / 带外原样 / root 不动** |
| 第 2 趟 topHead | **原样共享** | **平移** |
| 额外登记 | 无 | `leftHead == root` ⇒ `root._$6.add(newSub)` |

**五个最容易做错的点**（全部是实测踩实的，不是猜测；`docs/m2-engine-design.md` §12.1）：
1. ⛔ **"公式格一律 ≠16" 不等于"所有格都 ≠16"**：字面量格保留声明值 16（6 夹具共 72 个格）；
2. ⛔ **`extend_col` 的施力点是 `cell00._$5`**，不是"锚点的 head 链成员"（§5.5.5 第 3 条）；
3. ⛔ **`extend_col` 必须先于 `extend_row`**：顺序反了 19 锚点子格会落在第 4 行而不是第 8 行；
4. ⛔ **插行位置是行带之后 `endRow`**、量是 `rows*(count-1)`（不是 `count-1`）；
5. ⛔ **`_$3`（左 head）不调 `sameRowTypeAs`，`_$2`（上 head）调两次**，且两者命中分支判的 extend 分别是 18/19（§5.3.2）。

### 5.6 双矩阵与 `source` 语义

`source` 字段（JSON 输出 `calculated.cells[].source`）的**三个断言纪律**（附件 I.9）：

| 事实 | 证据 |
|---|---|
| `engine.sourceRow/sourceCol` **只在构造时写一次**；扩展**只改 `cell.row`，从不改 `sourceRow`** | `ExtNormalCell.java:127`；扩展调 `addRow(k)`/`addCol(m*cols)` |
| 扩展克隆出的实例**共享同一 `sourceRow`** ⇒ 同一模板格的 N 个实例 `src_row` 相同 | 实测 `engine_ext` 横向 19：5 个实例 `src_row` 全 = 4 |
| `source != null` ⟺ `r ≤ 模板行数 && c ≤ 模板列数`（两矩阵分工） | `ExtCellSet.java:623-629` |

三条硬约束：
1. ⛔ **不得**用 `src_row` 索引计算态网格（它是模板坐标）；
2. ⛔ **不得**用 `src_row` 反查模板行——同一模板行的多个实例 `src_row` 相同，反查**不唯一**；
3. 断言 `calculated` 段时，`src_row/src_col` 的期望值是**模板态坐标**，必须与**模板网格**比对。

> 实测补充：横向（19）克隆的**计算态行号归属**两夹具样本互相矛盾（`engine_ext` 落行 8、`engine_head_top` 留行 1）⇒ **不拟合行号**，只钉"同属一行 + 列走向"（附件 I.9）。

### 5.7 合并区 × 扩展（M2-04 / M2-08）

两块内容：

**① `expandLeftHead`/`expandTopHead` —— 块高的来源**（附件 I.8）：纵向扩展时，沿左 head 链、且 `containRow(this)` 成立的每个 head 的 `row_merge += rows*(count-1)`，并立即把该合并块在新坐标上重铺一遍（`ExtNormalCell.java:463-490`）。这就是"模板合并区跨进扩展行"时锚点 `row_merge` 变大的机制。

**② 合并区延续槽的两张矩阵分歧**（本项目 2026-10-13 产品 JRE 同对象实证，探针 `ProbeMergeAlias`/`ProbeTplSlot`）：

|---|---|---|

| `_$25` 引擎矩阵 | **锚点别名** | **独立槽**（src=(3,1) rm=1 ext=16） |

`mergeSame`（同值合并）**不在计算链路**：`ExtCellSet.mergeSame()` 只被 `SimplePager.createPages():133,:179` 与 `CalcSubRpt:138` 调用，`Engine.calc()` 从不调用 ⇒ 只能在**分页后**观测（`engine_samemerge` 单页夹具可在 P0 对拍）。

REPORT STUDIO · UNDERSTANDING LAYER

从元信息到业务语义，
再到可验证的 SQL

不要让 LLM 直接“猜 SQL”。先从数据库发现结构与证据，再建立可版本化的业务模型，将自然语言编译成查询计划，最后生成、验证并执行 SQL。

Schema → Business Model Semantic Query IR Query Planner SQL Compiler Feedback Loop
核心判断：元信息是业务模型的证据，不是业务模型本身。系统必须区分数据库中“观察到的事实”和由字段名、样本值、历史 SQL 推导出的“候选解释”；未经确认的业务口径不能伪装成确定事实。

01 · 总体架构

五层分工：每层只解决一类问题，LLM 不承担编译器和数据库的工作。

L1

Physical Schema · 物理结构

数据库能直接提供的证据
  • 表、列、类型、COMMENT
  • 主键、外键、索引
  • 枚举值、空值率、唯一性
  • 已有 SQL 与报表样例
↓ 结构分析与关系发现
L2

Business Model · 业务语义

把数据解释为业务世界
  • Entity / Fact
  • Dimension / Metric
  • Relationship / Grain
  • Business Rule / Policy
↓ 术语解析与意图绑定
L3

Semantic Query · 查询意图

表达“要查询什么”，不指定物理 SQL 细节
  • 指标与维度
  • 过滤与时间范围
  • 分组、排序、限制
  • 歧义与待澄清问题
↓ 粒度检查与查询规划
L4

Query Planner · 查询规划

确定数据源、关联路径与聚合策略
  • 选择事实源
  • JOIN 路径
  • 预聚合与去重
  • 粒度、权限、成本检查
↓ 编译与安全校验
L5

SQL Compiler · SQL 编译

确定性地输出目标数据库可执行 SQL
  • 方言与参数绑定
  • AST / 只读检查
  • LIMIT、超时、行数上限
  • 执行反馈与结果验证

02 · 从元信息发现业务模型

先自动发现，再记录证据与置信状态；不把猜测直接升级为业务事实。

结构证据

发现实体与关系

主键、外键、候选键、字段命名、引用基数、历史 JOIN。

产出：候选实体、关系边、关系基数与证据来源。

数据证据

识别粒度与值域

唯一性、空值率、枚举值、时间范围、重复率、值域重合。

产出：每行含义、字段角色、数据质量警告。

业务证据

发现指标与口径

COMMENT、报表模板、已确认 SQL、业务术语、用户纠错。

产出：指标候选、同义词、过滤规则与适用范围。

示例：从三张表推导候选业务图

orders(id PK, customer_id FK, amount, status, created_at)
customers(id PK, region_id FK, name)
regions(id PK, name)

Customer ── places ──> Order ── belongs_to ──> Customer
Customer ── located_in ──> Region

Order grain: one row per order
Customer grain: one row per customer
Region grain: one row per region

注意：外键可以证明结构关联，但不能自动决定“有效订单”的业务定义，也不能证明金额字段就是净销售额。

03 · 业务模型是核心资产

业务模型应独立于物理数据库、LLM Prompt 和报表版式，并且可以版本化、审查与测试。

Metric · 指标

指标不是一个字段名

net_sales
  source_fact: Order
  expression: SUM(order_amount)
  filters: [approved business rules]
  time_field: created_at
  grain: order
  format: currency
  status: draft | confirmed

正式口径必须由业务定义确认。例如退款、取消、折扣如何处理，不能从字段名猜出来。

Relationship · 关系

关系不仅是 JOIN 条件

Order.customer_id → Customer.id
  cardinality: many_to_one
  evidence: declared_foreign_key
  status: confirmed

OrderItem.order_id → Order.id
  cardinality: many_to_one
  evidence: inferred + data profile
  status: candidate

记录基数、来源、状态和适用条件，避免随意 JOIN、重复计数和未经验证的关联路径。

04 · 自然语言如何变成 SQL

LLM 负责把用户意图绑定到已注册的业务概念；规划器负责查询逻辑；编译器负责 SQL。

① 用户需求按地区统计最近三个月每月销售额和订单数
② 业务绑定net_sales、order_count、Region、Order.created_at
③ Semantic Query指标、维度、时间、过滤、排序；标记歧义
④ 查询计划事实源、JOIN 路径、粒度、聚合和去重策略
⑤ SQL 编译目标方言、参数绑定、只读校验与执行

Semantic Query（示意）

{
  "metrics": ["net_sales", "order_count"],
  "dimensions": ["Region", "Order.created_month"],
  "time_range": "last_3_months",
  "sort": [{"metric": "net_sales", "direction": "desc"}]
}

SQL（示意，需按真实口径编译）

SELECT
  r.name AS region,
  DATE_TRUNC('month', o.created_at) AS month,
  SUM(o.amount) AS sales,
  COUNT(DISTINCT o.id) AS order_count
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN regions r ON r.id = c.region_id
WHERE o.created_at >= :start_date
  AND o.created_at < :end_date
GROUP BY r.name, DATE_TRUNC('month', o.created_at)
ORDER BY sales DESC;

示例 SQL 使用了部分数据库方言语法，且未展示正式业务过滤条件；实际应由方言编译器和已确认指标定义生成。

05 · 最容易出错的地方：粒度

SQL 能运行，不代表指标正确。JOIN 后的行数变化可能导致金额、订单数重复计算。

数据对象记录粒度常见风险规划器需要做什么
orders一行一个订单连接订单明细后，订单金额被重复累加检查连接基数；必要时先聚合或分开计算
order_items一行一个订单商品明细COUNT(*) 被误当成订单数引用正确的订单指标或使用合适的去重策略
payments一行一次支付记录一笔订单多次支付，连接后产生重复行明确支付口径，必要时先按订单预聚合
库存快照一个商品在某时点的余额跨时间直接 SUM 库存余额使用期末、期初或时间加权等明确规则
比率指标分子与分母定义的业务总体直接对分组比率求和或简单平均先聚合分子、分母，再计算比率

06 · 验证与知识反馈闭环

错误要分类处理；确认过的结果才能沉淀为高质量样例或业务定义。

静态验证

编译前

字段是否存在、指标是否注册、JOIN 是否允许、粒度是否冲突、权限是否满足。
执行验证

运行时

只读账号、参数绑定、超时、行数限制、错误分类、结果形状与数据质量检查。
业务验证

用户确认

对照已知答案、业务不变量或用户确认；把纠错记录关联到模型版本和样例版本。
知识晋升原则：“SQL 执行成功”只能证明它在当前环境下可执行；“返回非空结果”不能证明业务语义正确。金样例应尽量附带期望结果、口径说明或可验证的不变量。

07 · 与现有 Report Studio 的边界

复用已有能力，不另造一套报表引擎。

现有能力建议定位需要补充
列元数据、COMMENT、枚举值物理 Schema 与证据层关系发现、粒度分析、证据状态
rpx-spec/v1报表结构与展示契约不要强行承担所有查询意图表达
模板库与 report list --query报表模板召回与 few-shot 示例需求、Spec、SQL、验证结果关联存储
spec analyze、lint、编译器静态分析与报表编译查询 IR、JOIN/粒度校验、SQL 安全校验
dataset inspect数据源试运行与诊断错误分类、限次修复、回归评测

08 · 实施路线

先构建确定性基础，再接入 LLM，最后形成持续改进闭环。

P0 · 发现

元信息 → 候选业务模型

  1. 提取 Schema 与约束
  2. 采样枚举值与数据分布
  3. 发现关系与候选粒度
  4. 输出可审查的模型文件

验收：每个候选结论都有证据和状态。

P1 · 查询

业务模型 → SQL

  1. 注册指标、维度、规则
  2. 生成 Semantic Query
  3. 构建查询 IR 与计划
  4. 编译、校验、试运行

验收：固定业务用例通过，结果粒度正确。

P2 · 学习

反馈 → 知识积累

  1. 保存已确认需求与查询
  2. 建立金样例检索
  3. 提出业务模型变更
  4. 持续运行回归评测

验收：经验可复用，正式口径不会被隐式改写。

原则 01事实与推断分离

观察到的 Schema 不等于业务定义；候选关系必须保留证据与状态。

原则 02查询与展示分离

Semantic Query 描述取什么数据；rpx-spec 描述如何组织和呈现报表。

原则 03验证优先于自信

模型、规划器和 SQL 都要接受可重复的检查与真实用例评测。

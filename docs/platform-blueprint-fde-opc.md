## 0. 结论先行

| 问题                    | 结论                                                                | 依据                                                 |
| --------------------- | ----------------------------------------------------------------- | -------------------------------------------------- |
| 现有能力能否成为 BI 系统的基础模块？  | **能，而且是 BI 里最难复制的那个模块**（编译 + 渲染 + 可复现运行）                          | 12 层参考架构加权完备度 **≈40/100**；但"报表编译器内核"维度 **≈88/100** |
| 现在这套东西是不是一个 BI 系统？    | **不是，差 6 层**（语义层、权限多租户、调度分发、缓存物化、自助交互、计费运维）                       | §3 逐层证据                                            |
| 该不该补成通用 BI 套件？        | **不该**。正面撞 Metabase / Superset / 帆软 / Power BI，复用度只有 25%          | §4 打分表                                             |
| 应该往哪走？                | **一个内核，三种外壳**：报表编译器（OEM）→ FDE 交付平台 → OPC 订阅服务                     | §4、§5                                              |
| 支撑 FDE / OPC 的关键不是仪表板 | 是**隔离工作空间 + 模板包 + Agent 接口 + 可审计产物 + 自动分发 + 计量**这 6 件"平台事"        | §8 收敛表                                             |
| 最高杠杆的单点补齐             | **语义层（指标层）**。没有它，FDE 每接一个客户都在抄 SQL，复用率≈0                          | §5.2、§9 P2                                         |
| 代码存量可带走多少             | **57,862 行 Rust 中约 71%（41,384 行）可直接带进平台**；平台层要从 321 行的 server 长出来 | §2.3                                               |

一句话：

> **这不是一个残缺的 BI，而是一个完整的"报表编译器"。把它当 BI 卖是降维打击自己；把它当编译器 + 交付平台卖，FDE 和 OPC 的商业模式都能直接压在它上面。**

## 1. 这个项目到底是什么（去掉包装后的定位）

### 1.1 一句话定义

> **把"报表"从一门手艺变成一次编译**：报表是 JSON 源码，引擎是纯函数，产物是带哈希的运行记录。

传统报表工具（FineReport / JasperReports / 甚至 Excel）的核心痛点是**不可复现**：改一个格式、换一份数据，结果就变了，没人知道上一版长什么样、为什么是这样。这套东西把报表变成了**编译产物**：

```
ReportDef(JSON) + Params + RowSets  ──引擎──▶  CalcGrid  ──▶  snapshot / xlsx / csv / print-*
        ↑                                        ↓
    sha256 修订                           run.json（revision + params + artifacts + diagnostics）
```

## 2. 能不能做 BI 系统的基础模块

### 2.1 用 12 层 BI 参考架构对照（权重 = 通用 BI 产品的价值占比）

| #  | BI 层           |      权重 | 本项目状态        |               得分 | 证据 / 缺口                                                       |         |            |
| -- | -------------- | ------: | ------------ | ---------------: | ------------------------------------------------------------- | ------- | ---------- |
| 1  | 数据接入 / 连接器     |      10 | 部分 60%       |              6.0 | 3 种 SQL + 2 种文件；**无连接池治理、无凭据保险箱、无 schema 探测**                 |         |            |
| 2  | 语义层 / 指标层      |      15 | **无 0%**     |              0.0 | `grep tenant`=0；dataset 就是裸 SQL/文件，无 dimension/metric/join 抽象 |         |            |
| 3  | 计算引擎           |      15 | 强 95%        |            14.25 | rpx-engine 26.6k 行零依赖                                         |         |            |
| 4  | 渲染 / 排版内核      |      10 | 强 95%        |              9.5 | snapshot + print 页映射                                          |         |            |
| 5  | 报表 / 仪表板编排     |      10 | 报表强·仪表板弱 50% |              5.0 | 报表 JSON 完整；图表是"格内图形 + ECharts 脚本"，非可拖拽 widget                 |         |            |
| 6  | 自助交互（透视/下钻/联动） |      10 | 弱 15%        |              1.5 | 无 pivot、无 drill、无 cross-filter                                |         |            |

| 8  | 调度 / 分发        |       5 | **无 0%**     |              0.0 | `grep cron`=0；\`smtp                                          | webhook | notify\`=0 |
| 9  | 缓存 / 物化        |       5 | **无 0%**     |              0.0 | `grep "\bcache\b" crates` = **0 次**                           |         |            |
| 10 | 元数据 / 血缘 / 审计  |       5 | 部分 40%       |              2.0 | 有 run.json 与 revision；无 catalog UI、无字段级血缘                     |         |            |
| 11 | 嵌入 / 集成 API    |       3 | 部分 30%       |              0.9 | 7 个只读路由；**无计算端点、无 embed token**                               |         |            |
| 12 | 运维 / 可观测 / 计费  |       2 | 弱 15%        |              0.3 | 无 metrics、无计量、无账单                                             |         |            |
|    | **合计**         | **100** |              | **≈39.95 / 100** |                                                               |         |            |

### 2.2 换一把尺子量同一个东西

| 评价维度                          |           得分 | 说明                     |
| ----------------------------- | -----------: | ---------------------- |
| 作为**通用 BI 套件**                | **40 / 100** | 缺 6 层，其中语义层与权限是"重做级"缺口 |
| 作为**报表编译器内核**                 | **88 / 100** | 只差 PDF 出口、缓存、能力自描述三件事  |
| 作为**Agent 可操作的报表运行时**         | **92 / 100** | 这是市面上几乎没人做对的位置         |
| 作为**可交付产品**（沿用 2026-10-17 评审） |     60 / 100 | 「功能已成型，生产化差最后一公里」      |

### 2.3 结论

**能，且应当只做"基础模块"，不要做"BI 系统"。**

理由不是能力不足，而是**价值密度**：

- 你手里的 88 分，是 BI 里最难写的部分（排版引擎 + 扩展语义 + 分页 + 确定性）。这部分竞品花 10 年做，且做得不如你"可测试"（743 个测试 + 逐格夹具）。
- 你缺的 12 分，是 BI 里最容易写、也最容易同质化的部分（仪表板拖拽、pivot）。补完只是"又一个 Metabase"。
- 你真正稀缺的 92 分（Agent 可操作），在 2026 年是**买方正在形成需求、卖方还没供货**的位置。

> 所以定位应该是：**"BI 的编译器后端" + "交付平台"**，而不是"BI 产品"。  
> 对外一句话：**你给数据和模板，它给你可复现的、能打印的、Agent 能改的报表。**

## 3. 三条产品路线怎么选（打分表）

| 形态                                 |  复用它要多少 | 上市时间（单人 + Agent） | 竞争                          | 客单价      | 运维负担      | 客户                 |      综合 |
| ---------------------------------- | ------: | ---------------- | --------------------------- | -------- | --------- | ------------------ | ------: |
| **A. 嵌入式报表引擎（OEM / SDK + Server）** | **92%** | 4–6 周            | 中（帆软 / Jasper / Stimulsoft） | 中        | 低（客户自己运维） | ISV、行业软件商、SaaS 厂   | **8.8** |
| **B. FDE 交付平台（咨询/实施团队用）**          |     75% | 10–14 周          | 低（几乎无对标）                    | 高（项目/席位） | 中         | 咨询公司、大厂数字化团队、系统集成商 | **9.1** |
| **C. OPC 报表订阅（SaaS）**              |     65% | 12–18 周          | 中高                          | 低（月订阅）   | 中高        | 中小企业、代账/财税/零售个体    |     6.5 |
| **D. 全功能 BI 套件**                   |     25% | 12+ 月            | 极高                          | 中        | 高         | 全市场                | **3.2** |

**推荐路径：A 做现金流 → B 做主攻 → C 作为 B 的自助降级版**（同一套控制面，不同计费与交付姿势）。

- A 的价值：把内核当标准件卖给"已经有客户、缺报表能力"的软件公司，**不承担终端交付风险**，6 周内就能收到第一笔钱，同时逼自己把 API/文档/兼容性做扎实。
- B 的价值：FDE 是当前 AI 落地里唯一"人效可放大"的角色。平台只要把"从客户数据到可交付报表"压到 1 人天，FDE 的毛利就是平台的定价上限。
- C 的价值：B 的副产品。B 里被反复交付 3 次以上的模板，脱敏后就是 C 的 SKU。

## 4. 目标架构：五平面

```
┌──────────────────────────────────────────────────────────────────────┐
│ L4 交付面  Delivery Faces                                            │
│  Agent 面(CLI/MCP)   FDE 面(设计器+工作区+模板包)                      │
│  OPC 面(自助控制台+计费+市场)   终端面(查看器+订阅+嵌入 token)           │
├──────────────────────────────────────────────────────────────────────┤
│ L3 控制面  Control Plane   ← 现在只有 321 行，要长成这一层              │
│  workspace/tenant · api-key · quota · schedule · secret vault         │
│  metering · audit event · delivery channel                            │
├──────────────────────────────────────────────────────────────────────┤
│ L2 执行与产物  Execution & Artifacts                                   │
│  run queue(异步/可取消) · worker pool · CAS 产物存储                  │
│  cache(key = rev+params+data_hash) · lineage event                    │
├──────────────────────────────────────────────────────────────────────┤
│ L1 语义与目录  Semantic & Catalog    ← 唯一的"新写"重头戏              │
│  source → model(join/dimension/metric/hierarchy) → dataset(编译后 SQL)│
│  metric binding：单元格只引用 m.revenue，不写 SQL                      │
├──────────────────────────────────────────────────────────────────────┤
│ L0 编译器内核  Compiler Kernel（不动）                                 │
│  rpx-model + rpx-engine + rpx-format + rpx-export                     │
│  契约：ReportDef + Params + RowSets → CalcGrid → Snapshot/XLSX/Print   │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.1 各平面的职责边界（不可越界）

| 平面     | 允许依赖                                   | 禁止                       | 理由                              |
| ------ | -------------------------------------- | ------------------------ | ------------------------------- |
| L0 内核  | 仅 std（model/engine），serde_json（format） | IO、网络、时间、随机、全局状态         | 已有 `gate.sh` G5 白名单守住；这是"可重放"的根 |
| L1 语义  | rpx-model（只读类型）+ SQL 方言                | 直接读文件/连库（由 L2 注入 RowSet） | 保持"编译期生成 SQL"，不引入运行期解释          |
| L2 执行  | L0/L1 + sqlx/fs                        | 业务规则、权限判断                | 执行层只做"跑 + 存 + 记账"               |
| L3 控制面 | L2 + 元数据库                              | 任何计算逻辑                   | 控制面挂了不影响已出产物                    |
| L4 交付面 | L3 的 HTTP API                          | 直连 L0                    | 所有外部入口必须过同一套鉴权与配额               |

### 4.2 关键设计决策（建议写成 ADR）

| #     | 决策                                                     | 理由                                                           | 反例代价                        |
| ----- | ------------------------------------------------------ | ------------------------------------------------------------ | --------------------------- |
| ADR-1 | **产物先行（artifact-first）**：一切结果 = 目录 + sha256，元数据库只做索引   | 已天然如此（`run.rs`/`library.rs`），坚持它就能白拿：去重、重放、租户迁移、备份 = `rsync` | 存 BLOB 进库 → 备份/迁移/审计全变重活    |
| ADR-2 | **计算无状态、纯函数**，缩放靠加 worker 不靠加缓存                        | 内核对齐，成本最低                                                    | 加会话/长事务 → 横向扩展立刻变难          |
| ADR-3 | **语义层编译期落地**：metric → SQL 在保存时编译并哈希，查询期不解释             | 可 diff、可评审、Agent 可读，且避免 LookML 那种运行期黑箱                       | 运行期解释 → 指标改动无法审计            |
| ADR-4 | **租户 = 目录命名空间**（`~/.rpx/tenants/<t>/ws/<w>/`），先不做 RBAC | OPC/小 FDE 阶段够用，一天能落地；数据库化留到多机                                | 一上来做 RBAC → 三个月没交付          |
| ADR-5 | **PDF 复用同一份打印 HTML + headless Chromium**，不写第二套分页       | `snapshot/paged.rs` 已产出页映射，`PrintPreview.tsx` 已验证渲染          | 另写 PDF 引擎 → 两套分页永远不一致       |
| ADR-6 | **能力自描述**：`rpx capabilities --json` 输出机器可读能力清单         | Agent 靠它决定"能不能做"，而不是试错                                       | 让 Agent 撞错 → FDE 的时间被错误消息吃掉 |
| ADR-7 | **错误协议带 `code` + `hint` + `docs_url`**                 | Agent 自愈率直接决定 FDE 人效                                         | 只给 message → 每次都人来兜         |

| GET/PUT | `/v1/reports/{id}`                    | 读写定义（已有读/写）              | 部分（`/reports/{id}` + PUT template） |
| POST    | `/v1/reports/{id}/runs`               | **触发计算**（幂等键，异步）         | **缺——最大断点**                        |
| GET     | `/v1/runs/{id}` + `/artifacts/{name}` | 轮询与取产物                   | 部分                                 |
| POST    | `/v1/embed-tokens`                    | 短时签名嵌入 token             | 缺                                  |
| POST    | `/v1/schedules`                       | 定时 + 分发                  | 缺                                  |

> **事实：`http.rs` 第 1 行注释写着 `No calculation handlers.`，路由表里刻意不存在 `POST /render`、`POST /export`（并有回归护栏测试）。也就是说——现在的服务端**不能算报&#x8868;**，只能读库和存模板。这是平台化的第一道门。**

## 5. 语义层：唯一的"新写"重头戏

### 5.1 为什么它排第一

| 场景             | 没有语义层           | 有语义层                             |
| -------------- | --------------- | -------------------------------- |
| FDE 接第 2 个客户   | 复制 30 份 SQL，改表名 | 换 source，指标复用                    |
| 财务口径改了（含税→不含税） | 逐报表改 SQL 或表达式   | 改一个 metric，编译所有引用                |
| 客户问"这个数怎么来的"   | 翻 SQL           | `metric → dataset → source` 三段可追 |
| OPC 卖模板        | 模板绑死表结构，无法复用    | 模板只绑 metric 名，可跨客户               |

**没有语义层，FDE 的复用率≈0，OPC 的边际成本≈线性。这两个商业模式都不成立。**

### 5.2 最小可用语义层（MVP，别做多）

```json
{
  "version": 1,
  "source": "pg_main",
  "tables": {
    "ar": { "table": "ar_invoice", "key": "invoice_id" },
    "cust": { "table": "customer", "key": "customer_id" }
  },
  "joins": [
    { "left": "ar", "right": "cust", "on": "ar.customer_id = cust.customer_id", "type": "left" }
  ],
  "dimensions": {
    "customer": { "expr": "cust.name", "type": "string" },
    "month":    { "expr": "date_trunc('month', ar.issue_date)", "type": "date" }
  },
  "metrics": {
    "amount":   { "expr": "ar.amount", "agg": "sum", "format": "#,##0" },
    "overdue":  { "expr": "ar.amount", "agg": "sum", "filter": "ar.days_overdue > 0" },
    "aging_ratio": { "expr": "overdue / amount", "agg": "ratio" }
  }
}
```

三条硬约束（对齐现有引擎哲学）：

1. **只支持单层 join 图 + 显式 `on`**，不做自动 join 推断（推断必然出错，且错误静默）。
2. **metric 必须可编译成单条 SQL**，编译失败即保存失败（不允许运行时兜底）。
3. **每个 metric 保存时算 `hash`**，报表引用 `hash` 而非名字——名字改了不影响历史报表的可重放（对齐现有 revision 哲学）。

### 5.3 与现有引擎的接缝

- `dataset` 仍是 `file | sql` 两型，**引擎完全不需要改**：语义层只是"帮你生成 SQL 的那一层"。
- 单元格表达式从 `pay.select(base+bonus)` 演进为 `m.amount`（`m.` 前缀 = metric 绑定），编译期展开成同样形态的 dataset。
- 因此**内核零改动**，这是这条路最值钱的地方。

## 6. FDE 工作流：平台要在每一步兜住什么

以"某零售客户要做一套 12 张的月结报表"为例：

| # | FDE 动作                                                        | 现状                                  | 平台必须补                                    | 目标耗时  |
| - | ------------------------------------------------------------- | ----------------------------------- | ---------------------------------------- | ----- |
| 1 | `rpx ws init --preset retail`                                 | 只能 `library init`，无工作区概念            | workspace + preset 包（含 model 骨架 + 12 模板） | 1 分钟  |
| 2 | `rpx source add --kind postgres --secret env:PG`              | 只有 `--datasources connections.json` | secret vault + 连通性/权限探测 + 表清单            | 10 分钟 |
| 3 | `rpx model introspect --source pg` → 人工/AI 修订 → `model apply` | 无                                   | schema 反射 + 候选 join/metric 建议 + 编译校验     | 2 小时  |
| 4 | `rpx preset list --industry retail` → `report create --from`  | 26 份模板无分类/无搜索/无克隆语义                 | 模板包格式、标签、脱敏、依赖声明                         | 10 分钟 |
| 5 | Agent 用 `--patch-file` 迭代 + `report validate`                 | **有**（这是强项）                         | 校验要 < 2s（fast path），否则 Agent 循环太慢        | 2 小时  |
| 6 | `rpx report run --export print-xlsx` → 交付                     | **无 PDF**（只能人肉另存）                   | headless PDF（同一份打印 HTML）                 | 30 分钟 |
| 7 | 客户批注 → 改 → 重出                                                 | 无批注载体                               | 结果快照 + 批注/对比（生成 v1/v2 差异）                | 1 小时  |
| 8 | `rpx preset extract --from <report> --as <preset>`            | **完全缺失**                            | 脱敏（去 DSN/绝对路径/客户字段）+ 自动补 `checks` 入画廊    | 1 小时  |

**当前估算：5–8 人天/单客户。目标：≤1 人天。** 差距集中在第 1、2、3、6、8 步——**没有一步是"BI 功能"，全是"平台能力"**。

> 第 8 步是 FDE 模式的复利点：**没交付过的能力不算资产，交付后能被抽取成模板的才算**。现在这条路是断的，等于每单都是首单。

## 7. OPC 工作流：平台要在每一步兜住什么

| # | OPC 动作      | 现状                                  | 平台必须补                                          |
| - | ----------- | ----------------------------------- | ---------------------------------------------- |
| 1 | 选一个行业包（SKU） | 无市场/无分类                             | 模板市场（分类/搜索/试用/授权）                              |
| 2 | 开租户         | 无 tenant                            | 自助开通（脚本或注册），15 分钟内出第一份报表                       |
| 3 | 收客户数据       | 只有文件路径/SQL DSN                      | 上传通道 + 只读库接入 + 数据留存与删除策略                       |
| 4 | 绑定期间/门店等参数  | **有**（参数模块 299 行 + `--params-file`） | 参数模板化（客户可自助填）                                  |
| 5 | 定时出报表       | 无 cron                              | 调度（含时区、失败重试、超时）                                |
| 6 | 分发          | 无 smtp/webhook                      | 邮件 / 企微 / 签名链接 / Excel 附件；带回执                  |
| 7 | 计费          | 无                                   | `cost_units`（run × 复杂度 + 存储）+ 月度账单可由 `run` 表还原 |
| 8 | 客户自助改一处     | 无 viewer 权限面                        | 表单化参数 + 只读视图 + 禁止改结构                           |

**OPC 的生死线不是功能，是"单客户月运维 ≤30 分钟"。** 上面 8 步里，现在只有第 4 步具备，其余 7 步都要人肉——这就是为什么"一人公司做 BI 服务"目前不成立。

### 7.1 两个角色如何收敛到同一套平台

| 需求       | FDE 要     | OPC 要    | 是否同一件事        |
| -------- | --------- | -------- | ------------- |
| 隔离工作空间   | 一客户一 ws   | 一租户一 ws  | ✅ 同一个能力       |
| 可复制模板包   | 行业预置 + 抽取 | SKU 上架   | ✅ 同一个能力（两种呈现） |
| Agent 接口 | 我在现场改     | 我没空点鼠标   | ✅ 同一个能力       |
| 可审计产物    | 客户要溯源     | 纠纷要举证    | ✅ 同一个能力       |
| 自动分发     | 交付给客户     | 订阅推送     | ✅ 同一个能力       |
| 计量计费     | 按项目报价     | 按 run 计费 | ✅ 同一个能力       |
| 自助仪表板    | 不需要       | 弱需要      | ❌ 不必先做        |

> **结论：FDE 与 OPC 的公共需求集 = 平台层 6 件事，与"BI 自助分析"几乎不重叠。**  
> 这就是为什么"先做平台层、后做仪表板"不是妥协，而是唯一正确的顺序。

## 8. 路线图（4 阶段，含验收）

| 阶段                 | 周期（单人+Agent） | 交付物                                                                                                                          | 验收标准（可证伪）                                                    |
| ------------------ | ------------ | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **P0 可交付单机版**      | 2–3 周        | ① `capabilities --json`<br />② `POST /runs` 异步 + 取消<br />③ headless PDF<br />④ `preset extract` + 脱敏<br />⑤ 错误 `code/hint` 表 | 一个没看过代码的人，凭文档在 **1 天内**从一份 CSV 交付出 A4 打印稿；PDF 与打印预览逐页像素差 = 0 |
| **P1 多租户控制面**      | 3–4 周        | tenant/workspace/api-key/quota/metering/event；CAS 产物存储；cache；schedule + 邮件·企微分发                                              | 3 租户并发跑批互不影响；停掉控制面不影响已有产物下载；月度账单可由 `run` 表 100% 还原           |
| **P2 语义层**         | 3–4 周        | `rpx-semantic`：source/model/dimension/metric/join/hierarchy → 编译 SQL + manifest；catalog API                                  | 同一 metric 被 3 张报表引用；改定义一处生效；所有历史报表仍可重放（hash 不变则不重算）          |
| **P3 FDE/OPC 交付面** | 4–6 周        | 模板市场、embed token、只读 viewer、订阅、计费对接                                                                                           | 新客户 **15 分钟**自助开通并拿到第一份报表；0 人工介入；单客户月运维 ≤30 分钟               |

**总周期约 12–17 周**（含被真实客户打断的余量）。每个阶段都可单独卖：

- P0 完成即可卖 A（OEM 引擎）；
- P1 完成即可接第一个付费 FDE 项目；
- P2 完成后模板才有复用价值；
- P3 完成后 OPC 模式才成立。

**阶段顺序不可交换**：先做 P3 的仪表板 = 在沙地上盖楼；先做 P2 语义层而无 P1 隔离 = 多客户数据混在一起，返工。

## 9. 明确不做（Non-goals）及理由

| 不做                | 理由                                           | 替代方案                                          |
| ----------------- | -------------------------------------------- | --------------------------------------------- |
| 拖拽式自助分析 / 透视表     | Tableau/PowerBI/Metabase 主场，补它 = 重做 6 个月且打不过 | 让 Agent 生成报表；客户要探索就给他 Excel 导出                |
| 实时流 / OLAP cube   | 与"可复现"哲学冲突；运维成本 > 收益                         | 定时批跑 + cache；需要实时就接外部数仓                       |
| 移动端原生 App         | 交付价值低，审核成本高                                  | 响应式 H5 + 签名链接                                 |
| ML 预测 / 智能洞察      | 与报表编译器无关，叙事会散                                | 留 API 给外部模型                                   |
| 完整 RBAC（角色/资源/继承） | 早期过度设计，拖死交付                                  | 租户 + 3 角色（owner/editor/viewer）+ api-key scope |
| 报表设计器多 sheet（引擎级） | ROI 低于语义层；且单 sheet + 多报表已能覆盖                 | 用"报表组"（一个 run 出多个文件）替代                        |
| 自研 PDF 排版引擎       | 双分页必然不一致                                     | headless Chromium 打同一份打印 HTML                 |

## 11. 风险、假设与未验证项

| #  | 风险/假设                        | 类型           | 缓解                                               |

| R2 | 语义层设计过度（变成第二个 LookML）        | 架构风险         | 只做 §5.2 那个最小集；任何新概念必须"能编译成单条 SQL"才准入             |

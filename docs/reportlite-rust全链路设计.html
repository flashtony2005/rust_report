6.1 扩展算法（extendRow / extendCol）✅ 已落地

已按 Java 结论落地（stage_a / stage_b / ext_algo.rs / heads.rs）， 执行顺序清单 = docs/m2-engine-design.md §12（动工前读它）。三阶段拆解：

  1. 阶段 A｜建格（stage_a.rs）：模板 → 两张矩阵；合并锚点铺满矩形，后续格按自身内容覆盖；rowType==-90 一次性 latch 为分组头（引擎从不合成它）
  2. 阶段 B｜准备（stage_b.rs，顺序即契约）：checkExtend 决定谁是扩展格 → 逐格 head 赋值 + 16 按拓扑改写成 17/18/19（两条写入路径，均只在 expression != null 时生效）→ head 链归一化到最近的扩展格
  3. 阶段 C｜求值调度（eval/sched.rs）：扩展本体 extend_col / extend_row（ext_algo.rs，算法正文 = format-contract.md 附件 I）在 channel4 的 19/18 趟里触发——每趟 = 包络计算 → 克隆附属格 + 插行/插列平移 → 重连 head
⛔ 三条实测顺序雷区（全部有夹具证据）：① extend_col 必须先于 extend_row（反了 19 的子格落第 4 行而非第 8 行）；② 16 改写只对带表达式格生效——字面量格保留 16（6 个夹具共 72 格如此）；③ extend_col 的施力点是 cell00._$5，不是"锚点 head 链成员"。
主格自动长高：expandLeftHead() 沿链上溯，head.contain_row(this) 成立就 rowMerge += mergeInc（expandTopHead 横向同构，但施力点不同）。左侧"部门"大格随右侧明细拉高，不是渲染技巧。

七、数据源设计（rpx-ds） ⏳ M3 规划

7.1 选型：libSQL（Turso）

数据库职责边界先厘清：Turso 只做平台库（报表资产 / 参数 / 数据源配置 / 结果缓存）， 业务取数仍走报表自己的数据源（SQL/File/EsProc 等，见 7.2）——两者互不替代。

维度libSQL（Turso）本地模式rusqlite（纯 SQLite）sqlx + PG结论
部署形态嵌入式单文件（new_local(path)；不做远端同步 / replica）仅嵌入式单文件必须独立服务器libSQL
文件格式与 SQLite 完全兼容，sqlite3 CLI / DB 工具可直接打开原生私有格式libSQL
开发体验SQLite 方言零学习成本；async execute/query + params!/named_params!同步 API 更啰嗦query! 宏编译期校验libSQL
报表场景读多写少（渲染并发读、写串行）；快照缓存即一行记录同左重，单机部署反而累赘libSQL
CLI 对拍new_local(":memory:") 起步，M1/M2 完全不需要起服务同样可以必须先装 PGlibSQL
ORM不需要（行集直取）同上sea-orm 可为 PG 加分但场景不匹配裸 libsql
只用本地模式，不要远端：这是明确的部署边界——单实例、私有化、离线可用。 理由：① 报表资产与渲染缓存的写入方只有服务本身，没有多节点写冲突，也就没有同步需求； ② 私有化交付最常见的要求就是"断网可跑"，远端协议一旦成为依赖，离线降级反而要额外做； ③ 运维成本归零——备份 = 拷一个 .db 文件，迁移 = 拷走，没有任何外部服务要盯。

取舍说明：放弃 sqlx 的编译期 SQL 校验，换来"零依赖服务"的对拍能力和单文件部署。 SQL 正确性靠 CLI 对拍测试兜底——反正报表的 SQL 是用户模板里带的，本来就不是我们写的。

关于 libSQL vs rusqlite 的诚实说明：只跑本地模式时，libSQL 的增量价值主要是 async API 和 Turso CLI 生态（文件格式仍与 SQLite 兼容）。若日后想接云端，只需把 new_local 换成 new_remote_replica 一行，不必改调用方——但这个升级路径本期不启用。 
// libsql = { version = "0.x", features = ["core"] }   // 仅本地模式，不引入 replication / remote
let db = libsql::Builder::new_local("rpx.db").build().await?;
let conn = db.connect()?;
conn.execute("INSERT INTO reports (name, rpx) VALUES (?1, ?2)",

7.2 业务数据源：多数据库支持（sqlx AnyPool + 方言层）

报表的取数必须能连多种业务库（财政工资库在 PG、台账可能在 MySQL、本地小库在 SQLite/Turso）。 用 sqlx 的 AnyPool：同一个查询 API，运行时按 URL 前缀选驱动—— postgres:// / mysql:// / sqlite://（0.8 起还有 mssql://）， 换库只换连接串，代码零分支：

// Cargo.toml: sqlx = { features = ["any", "postgres", "mysql", "sqlite", "mssql", "runtime-tokio"] }
sqlx::any::install_default_drivers();        // 必须：否则 AnyPool 直接 panic
let pool = sqlx::AnyPool::connect(&ds_cfg.url).await?;
let mut rows = sqlx::query(&ds_cfg.sql).fetch(&pool);   // 同一条代码路径跑任意库

方言层要处理的差异（实测要点）

差异点PostgresMySQLSQLite/libSQLMSSQL
占位符$1? / ?1?1@p1
分页LIMIT/OFFSETLIMIT/OFFSETLIMIT/OFFSETOFFSET…FETCH
布尔true/false1/0（tinyint）1/01/0（bit）

类型映射统一收敛到 DsValue{Null,Bool,I64,F64,Str,Blob,Decimal,Date}；BigDecimal 走 rust_decimal 保精度
三个必须认的坑： ① install_default_drivers() 不调用 AnyPool 直接 panic； ② AnyPool 没有 query! 宏级编译校验——报表 SQL 是用户模板里带的，本来就不受我们控制， 正确性靠 CLI 对拍 + 渲染期报错定位兜底； ③ SQLite/libSQL 同时只有一个写者，池按库种配置（sqlite 类 max_connections=1，网络库 10+）。 另外大报表分页 SQL 要按方言生成（_rowsBefore_ 在 MSSQL 上就是 OFFSET…FETCH）。

连接管理

  • 池注册表：RwLock<HashMap<ds_id, AnyPool> 懒加载，首次渲染该报表时建池；池随配置变更失效重建。
  • 凭据与配置分离：Turso 里只存非密配置（kind/url/池参数），密码走环境变量/Vault 引用，不出现在库表和日志。
  • 并发预算：单报表渲染 = 1 次取数 + 内存计算；总并发连接数受各业务库池上限约束，超限进队列而非新建连接（对应 Java PerfMonitor 的预算思路）。

7.3 插件式数据源（Java 工厂的 Rust 等价）

Java 靠 Class.forName(dsc.getFactoryClass()) 实现"引擎不认识任何数据源类型"。Rust 用 trait 对象，更类型安全：

pub trait DataSource: Send + Sync {
    fn kind(&self) -> &'static str;               // "sql" | "file" | "builtin" | "turso" …
    fn async fn fetch(&self, cfg: &DataSetConfig, args: &Args)
        -> Result<RowSet>;
}
// 注册表：启动时 insert(kind, Arc<dyn DataSource>)，按 datasources.kind 路由
// SQL 类内部再按 url scheme 选 AnyPool 驱动 —— 两级分发，互不感知
// 新增数据源 = 新增一个实现 + 一行注册，引擎零改动（与 Java 工厂同一理念）

7.4 数据集模型与 cross（多数据源对齐）

pub struct RowSet {
    columns: Vec<Column>,          // 列式存储：列名 + 类型化数据
    titles: HashMap<String,String>,// 英文字段 → 中文别名（getColNoFromTitle）
    len: usize,
}
// Row.getData(0) 固定返回行号（第 0 列内置）；getData(name) 查不到回退中文别名
Row.cross() 的 Rust 实现：Java 用对象身份做半连接（命中返回自身，否则 NullRow——不是 null 而是合法空值载体，跨库表达式 A.x * B.y 不匹配时继续传播空值而非 NPE）。Rust 侧装载数据集时预建 HashMap<JoinKey, RowIdx>，cross 即一次哈希查找，miss 返回 RowRef::Null。一次物化 + 内存查找，避免 Java 里逐行回调的开销。

11.3 正解：服务端 Rust 产 PDF（rpx-print）

关键优势：分页语义引擎里本来就有。Java 侧 SimplePager（3403 行）已经实现了 按行高累加断页、固定区高度预扣、分组头跨页重绘、分栏、表头表尾重绘——Rust 引擎算完扩展之后， 手里就是带合并区的扁平矩阵 + 行高列宽 + 分页水位，这正是 PDF 排版需要的全部信息。 不需要第二个渲染引擎，也不需要 canvas 物化。

pub struct PageLayout {                 // 来源：.rpx 报表属性 + 用户打印时覆盖
  paper: Paper,                    // A4/A3/Letter/Custom(w,h) —— 对齐 PrintPaperSize
  orientation: Orientation,        // Portrait | Landscape
  margin: Margin,                  // 支持左右不对称（对齐 PrintPaperMargin）
  scale: Scale,                    // FitWidth | FitPage | Percent(f64)
  repeat_rows: Vec<usize>,          // 每页重复的行（对齐 PrintFreeze.Row / 润乾"报表首格"）
  header_footer: HeaderFooter,     // 页码 / 表名 / 自定义文本，支持整本连续页码
}
// rpx-print：PageLayout + Vec<Page>（分页后的矩阵）→ printpdf Document → Vec<u8>
// printpdf：纯 Rust，文字/字体/线条/矩形/图片/页面尺寸齐全，无外部依赖、无头可跑
  • 与 .rpx 的对应（打印配置已解析 ✅）：rpx-core 的 print_setup.rs 已把首个 MetaData 的 33 槽全量解出（纸张 / 四边距 / 纵横 / 分栏 layout / 页眉页脚模式 / pager_style…，契约 = format-contract.md 附件 D）； 报表级另有 dispRatio(133)、unit(1=MM)、expMap 码 33=每页行数—— PageLayout 的字段几乎可从这两处直接映射，用户无需重设。
  • 确定性输出：同样输入永远得到同一份 PDF（无浏览器版本差异、无字体嗅探差异），便于归档与审计。
  • 零授权、零部署依赖：不引 Chrome，符合"私有化、断网可跑"的既定边界。
  • 大报表：与 BigEngine 分页同源——算一页写一页，PDF 也是流式产出，内存不随总页数增长。

11.6 打印排版算法（落地细节，不依赖任何第三方实现）

这部分是"思路"的本体。全部来自已逆向理解的 ReportLite 分页器（SimplePager，3403 行）与标准 paged-media 语义， 不来自任何商业组件的反编译——既无授权风险，也已经被对拍验证过。

① 页面盒模型

printable_w = paper_w - margin.left - margin.right      // 边距支持左右不对称
printable_h = paper_h - margin.top  - margin.bottom
repeat_h    = Σ row_h[repeat_rows] × scale              // 每页重复的表头高度
avail_h     = printable_h - repeat_h - header_h - footer_h   // 页眉页脚也占可印高度

② 缩放（对齐 PrintScale）

模式算法超出时
FitWidthscale = printable_w / content_w，clamp 到 [0.1, 4.0]低于 0.1 → 转横向分页（拆列），不无限缩小
FitPagescale = min(printable_w/content_w, avail_h/content_h_total)一次性塞进一页，字号随 scale 同步缩放
Percent(p)scale = p / 100超出 → 横向 + 纵向同时分页

横向分页（对应润乾 BaseExcel 的列拆分）：按列宽贪心累加，超过 printable_w 即断页； 合并格跨断点时整格移到下一页（保内容完整，不裁切），这与 Java 侧"锚点 + 跨度"的处理一致。

③ 纵向断页（与 SimplePager 同构的水位算法）

watermark = 0
for row in rows:
    need = fixed_top_h(row) + row_h[row] × scale      // fixed_top_h = 分组头/小计/合计行高
    if watermark > 0 && watermark + need > avail_h:
        emit_page(); watermark = repeat_h             // 换页后表头重绘，水位重置
    place(row); watermark += need
// keep-together：分组行与其子行不可被分页拆开（rowType 分组），
// 需把「整组高度」提前参与上面的越界判断，否则会出现半截分组。

两个从逆向结论里直接搬过来的要点：固定区高度要先扣（分组头跨页重绘靠祖先链计算）， 水位单向推进不回头——这两条保证了分页结果确定、可复现。

④ 页眉页脚与页码

页码两种 scheme（对应官方 PrintHeaderFooter 的语义差异，报表场景两种都有人要）：

  • 整本连续：跨 sheet 累加全局页序，适合"一个报表打 30 页、页码 1/30…30/30"
  • 每表独立：每张表从 1 开始，适合多表合订本
  • 元素：页码（第 X 页 / 共 Y 页）、表名、打印时间、自定义文本；左右中三段对齐

⑤ 文本度量（中文 PDF 的生死线）

  • 文本宽度必须来自字体度量，不能用字符数估算——中文全宽、数字半宽混排时误差会累积到列宽判定上。
  • 中文字体子集化内嵌（思源黑体/宋体），否则 PDF 在未装该字体的机器上乱码；子集只收实际用到的字形，控制在几百 KB。
  • 行内换行按可印宽度逐字断行，标点避头尾（中文排版基本规则，财政报表会被逐字看）。

⑥ 备选路线：canvas 物化（不选，仅记录）

若将来要在浏览器里打印 Univer 的 canvas 内容，唯一办法是离屏 canvas 按打印 DPI（300）分块 → toDataURL/blob → 当图片贴进页面。缺点很硬：文字不可选不可搜索、300dpi A4 约 3500×4960px 导致文件体积暴涨、 内存峰值高、缩放后发虚。我们的场景根本不需要它——引擎产出的是逻辑矩阵，直接走 printpdf 矢量输出。

关于"反编译 Univer Pro 找思路"的决定：不做，也没必要。 ① 合规：Pro 是商业授权组件，其许可协议与通常的商业 EULA 一样禁止反编译/反汇编， 而这是要进财政场景私有化交付的产品，授权链瑕疵会在验收/审计阶段暴露； ② 拿不到：官方已暂停新购与 30 天试用，现在连合法的黑盒观察渠道都没有； ③ 不需要：分页与打印的全部语义我们已经有完整源码级参考实现（ReportLite SimplePager， 已逆向并逐行理解），上面的算法就是它的 Rust 化，比从混淆产物里猜更可靠。 若确实需要研究 canvas 表格的打印机理，合法材料是 Univer 开源部分（Apache-2.0，GitHub 可读）， 但打印插件本身不在开源范围内。

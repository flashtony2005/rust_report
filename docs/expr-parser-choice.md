# expr-parser-choice — 手写 Pratt vs nom（功能对比）

| 项 | 值 |
|---|---|
| 对比对象 | 现有手写解析器（`crates/rpx-engine/src/expr/`） vs 引入 `nom` 重写 |
| 日期 | 2026-10-13 |
| 触发 | 用户指令「用 nom 去实现」，需先弄清 nom 到底能买到什么 |
| 性质 | **只做对比，不改代码**。`expr/` 一行未动 |

---

## 0. 结论速览

**在这个仓库里，nom 对表达式解析买不到"语义正确性"，却要付出三样东西：零依赖不变式、重写已验证代码、错误契约重对齐。**

原因是：本项目的表达式"解析器"难点**不在语法**（语法是一张扁平的优先级表，Pratt 用约 90 行解决），
而在**词法怪癖**与**与 Java 的逐行对应**——而这两样 nom 都不提供，**你仍然要自己写**。

nom 在本仓真正合适的位置是 `.rpx` 的**二进制**记录层（`rpx-core/reader.rs`），但**那部分已完成且经变异测试验证**。

---

## 1. 现状：这个"解析器"到底是什么（实测）

`expr/` 共 19 个文件。与解析相关的部分：

| 文件 | 行数 | 作用 |
|---|---|---|
| `token.rs` | 120 | token 集与 `is_delimiter` |
| `lexer.rs` | 229 | 扫描（**`Expression.scanId` 的逐字移植**） |
| `parser.rs` | 219 | 手写 Pratt（核心约 90 行） |
| `atom.rs` | 179 | 原子 → 节点 |
| `call.rs` | ~90 | 参数切分与调用组装 |
| `classify.rs` | 163 | 中缀表 + 统一"不支持"出口 |
| `ast.rs` | 286 | 节点定义 + `is_extend()` 谓词 |

### 1.1 关键事实：词法器**不是**通用 tokenizer

它是产品 `Expression.scanId`（`Expression.java:70-78`）的**逐字移植**，有三处不能改的怪癖：

1. **分隔符集合是固定的 19 个字符**：`空白 + - * / % = & | ! : , > < ( ) [ ] { }`（`lexer.rs:9-13`）。
2. ⛔ **`.` 不在分隔符里** ⇒ `ds1.select` 被**整体吃成一个 `Tok::Word`**。
   这正是 `Expression.java:174` 能用 `id.indexOf('.')` 切出数据集名的前提。
   于是 `A1` / `$B2` / `123.45` / `1e5` / `ds1.select` **全都是 Word**，
   **类型判定被推迟到语法层**（`lexer.rs:37` 明写："本层只切原子，不判类型"）。
3. **字符串反转义 = `Escape.remove`**（`Escape.java:173-214`），含一个反直觉细节：
   **结尾孤立的 `\` 被整段丢弃**，不是保留（`lexer.rs:224-225`）。

### 1.2 语法部分：确实是"轻"的

- 三条位置规则（前缀 `!`/`not`/`&`=16、后缀 `(`/`[`=17、前缀 `-`/`+`=18、原子=19），
  绑定力**直接取产品源码的 `priority`**，两边不会漂移（`parser.rs:20-28`）。
- `(...)` 与 `[...]` 后缀都归约成同一个 `Expr::Index`，**参数刻意丢弃**——
  因为 `is_extend()` 只看树形、不看参数（`parser.rs:99,106`）。

⇒ **"语法"这一层，是本次对比里唯一 nom 真正对口的层，而它恰恰是最简单的一层。**

## 2. 逐项对比

| 维度 | 手写（现状） | nom |
|---|---|---|
| **词法怪癖保真** | 逐行可对照 `file:line`（`.` 不分隔、`scanId` 吃到分隔符、孤立 `\` 丢弃） | ⛔ **怪癖不会消失** —— 你仍要写同样的字符级识别器，只是换成组合子写法。**这一层没有净收益** |
| **运算符优先级** | Pratt **内建**，约 40 行主循环 | ⛔ nom **没有**内建优先级支持；要么自己手写优先级爬升，要么再引 `precedence` crate（**又一个依赖**） |
| **类型判定推迟** | 天然：Word 交给 `atom.rs` 分类 | 需要刻意把"识别 Word"与"解释 Word"分开，否则容易写成一个巨型 `alt()` |
| **错误契约** | `UnsupportedExpr { expr }` + 中文细节串，**已有测试断言**（如 `"表达式不能以 X 开头"`） | 需把 `nom::Err<Error>` 包装成同形；`nom` 的 `ErrorKind` 与本仓文案**不是一回事** |
| **与 Java 的 `file:line` 溯源** | **一对一**：每条规则旁边就是 Java 行号 | 组合子抽象引入中间层，溯源变间接（本项目最核心的价值会被稀释） |
| **依赖成本** | **0** | `nom` + `memchr` + `minimal-lexical`；且 **`rpx-engine` 必须移出 G5 零依赖层** |
| **编译时间 / 体积** | 最小 | 增量（不致命，但白拿的） |
| **性能** | 非瓶颈（表达式是一小段字符串） | 非瓶颈 ⇒ **买不到东西** |
| **增量 / 流式解析** | 不需要 | 不需要（`nom` 的强项在这里用不上） |
| **二进制格式解析** | — | ✅ **这才是 nom 的强项**，但见 §3 |
| **已有测试** | 4 组：`tests.rs`(302) / `tests_eval.rs`(296) / `deviation.rs`(251) / `wiring_tripwire.rs` | ⛔ 全部要重跑重验，且**重验只能证明"新实现也过"，不能证明"更对"** |

## 3. nom 真正合适的位置（不在 expr）

nom 同时也是**二进制**解析器（`nom::number::complete::be_i32` 等）。本仓最对口的是：

- `rpx-core/reader.rs` —— `.rpx` 的记录层（int32 长度前缀 + 定长切片）与
  **19 标签对象字典**（`-1`=null / `0`=IRecord 多态 / `1`=短字符串 / `13`=长字符串 / `2`=BigDecimal …）。
  这是一个**真正的**带标签二进制格式，nom 的 `alt()` + 长度前缀组合子在这里是自然表达。

**但是**：这部分**已经完成**，且经独立验证方的变异测试 **24/24 全杀**（`spec-m1.md:366-368`）。
把它换成 nom，等于**用一个未验证的实现替换一个已验证的实现** —— 收益为负。

⇒ **nom 在本仓没有一个"既合适、又还没做"的位置。**

---

## 4. 决策矩阵

| 如果你想要的是… | 手写 | nom | 建议 |
|---|---|---|---|
| 表达式解析**正确性** | 已有 + 已验证 | 要重验 | **手写** |
| 表达式解析**可读性** | 90 行核心 + 显式位置规则 | 组合子更"声明式"，但怪癖仍要手写 | 平手，略偏手写 |
| **错误信息质量** | 中文细节，已对齐产品 | 需额外包装 | **手写** |
| **零依赖不变式** | 保持 | **失去** | **手写** |
| 将来**语法大幅变复杂**（如 M3 需要新文法） | 要自己加 | 组合子更省事 | 那时再评估 |
| `.rpx` 二进制层 | 已有 + 已验证 | 更对口但已完成 | **不动** |

## 5. 如果仍要引入 nom：代价清单（必须先认下来）

1. `rpx-engine` 从 **G5 零依赖层**移入受审白名单（`docs/code-review.md` §3.2），
   并在登记表写"为什么替代方案不行"——**这一条与"分层白名单、保住核心零依赖"的意图直接冲突**。
2. 重写 `lexer.rs` + `parser.rs`（+ 可能 `atom.rs`/`call.rs`），**重跑全部 4 组测试**。
3. 重验方式必须能证明"新实现与旧实现同构"，而不只是"新实现也过测试"——
   建议：**保留旧实现作为 oracle**，对全部夹具表达式逐条比对两版 AST 相等（这才是本仓的证明标准）。
4. 若走这条路，`merge.rs`（M2-08/21）应**先做完**，避免同时动两块已验证代码。

```sh
# 1. 全仓是否已用 nom（应 0 命中）
grep -rnE 'use nom|nom::' crates/

# 2. 词法器的分隔符规则（`.` 不在其中）
sed -n '9,17p' crates/rpx-engine/src/expr/lexer.rs
grep -nE 'is_delimiter' crates/rpx-engine/src/expr/token.rs

# 3. 语法核心规模（Pratt 主循环 + 前缀）
sed -n '93,166p' crates/rpx-engine/src/expr/parser.rs

# 4. 绑定力直接取自产品 priority
sed -n '18,28p' crates/rpx-engine/src/expr/parser.rs

# 5. rpx-core 已暴露 merge 槽（M2-08/21 的地基）
grep -nE 'merge_same|merge_null' crates/rpx-core/src/cell.rs
```

> ⚠ 用 `grep -E`。本机 BSD grep 的 BRE 下 `\|` 是字面量，会**静默返回 0 行**（见 `code-review.md` §5.12）。
